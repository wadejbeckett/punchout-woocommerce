# Test suite

Pure-PHP unit tests for the layers that carry the protocol and security guarantees: the cXML codec (parser, builder, form packing, money boundary), one-time tokens, replay policy, the session state machine, secret sealing/dual-slot verification, CIDR matching, the rate-limit window, the per-partner ALL-CAPS transform, the button label resolution (setting, default, filter order), the checkout path (the payment method, Submit, the order's cXML, validation, the lifecycle, the late Submit, provenance, the visit's account), the state page, the leave question, Cancel and return, and the Punchout Quote order rules. **No WordPress, WooCommerce or database is required or loaded** — calls across those boundaries use guarded stubs.

Quote creation, conversion and retention are stubbed, not integrated: `tests/Support/wc-stubs.php` records order changes and query arguments, returns fixture query IDs, and can inject false updates or thrown failures. These tests prove our lines, prices, metadata, status, notes, delivery address, failure containment and audit rules. Retention tests check disabled/empty sweeps, bounded oldest-first querying with a UTC timestamp cutoff, missing/stale orders, cancellation counts, repeat sweeps and continuation after an individual failure. The query stub does not implement database filtering or date parsing. Nothing here proves WooCommerce stock, email or persistence behaviour; conversion to Processing/On hold intentionally keeps native real-order effects. Those require staging checks.

Five support files load from `bootstrap.php`: the TestCase shim, the two stub files below, the setup I/O seams, and the shared quote service doubles. The stub files own disjoint symbol sets — the `function_exists`/`class_exists` guards protect each symbol individually, but two files claiming one symbol makes the winning body depend on require order. Check the other file before adding to either:

| File | Owns |
|---|---|
| `Support/wp-stubs.php` | the WordPress surface: `__`, `_x`, `_n_noop`, the `esc_*` family, `apply_filters`, `locate_template`, the nonce pair, `nocache_headers`, `wp_unslash`, `sanitize_text_field`, `sanitize_title`, `wp_strip_all_tags`, `get_option`, `wp_parse_args` (array arguments only), `home_url`, `wp_parse_url` (absolute URLs only), `status_header`, the transients (`get_transient`, `set_transient`, `delete_transient`), `wp_mail`, `get_current_user_id`, `is_user_logged_in`, `wp_get_current_user`, `wp_get_session_token`, `wp_set_auth_cookie`, `wp_set_current_user`, `wp_clear_auth_cookie`, `WP_Session_Tokens`, `wp_json_encode`, `HOUR_IN_SECONDS`, `MINUTE_IN_SECONDS`, `ARRAY_A`, `is_wp_error` and the class `WP_Error` |
| `Support/wc-stubs.php` | the WooCommerce surface: `get_woocommerce_currency`, `WC`, `wc_create_order`, `wc_get_order`, `wc_get_orders`, `wc_get_product`, and the classes `WC_Order`, `WC_Order_Item_Product`, `WC_Product`, `WC_Customer`, `POW_Test_WC` |

### The per-visit login surface, and what is deliberately absent

One customer account holds one login, and each punchout visit gets its own WP auth cookie, its own `WP_Session_Tokens` entry and its own WooCommerce session row. The stubs are shaped so a cross-visit test cannot pass vacuously. `wp_set_auth_cookie` records each call in `pow_test_auth_cookies` (user id, remember flag, secure flag and the visit's token), `wp_set_current_user` moves `pow_test_current_user_id` and appends the switch to `pow_test_current_user_switches`, and `WP_Session_Tokens` is keyed per user **and** per token, so destroying one visit's token leaves every other visit of that account verifiable. `wp_get_session_token` answers from the per-visit list `pow_test_login_tokens` under the cursor `pow_test_login_token_index` — the same answer for every call inside one simulated request, a different one in the next — and falls back to the single `pow_test_login_token` when no list is set. `apply_filters` passes its trailing arguments to the callback, which is what lets an `attach_session_information` filter see which account it is decorating.

No stub exists for `wp_insert_user`, `wp_update_user`, `wp_delete_user`, `wp_create_user`, `wp_generate_password`, `update_user_meta`, `add_user_meta`, `delete_user_meta`, `add_role` or `remove_role`, and none may be added. The plugin never creates, renames or deletes users and never writes user meta on the bound account; an absent function fails loudly where a fake would quietly pass. A suite that genuinely needs to observe such a call defines a namespace-local seam that binds only inside itself (`Unit/CompanyBookTest.php`). `add_filter`, `remove_filter` and `add_action` are absent for a different reason: the global hook surface belongs to `fixtures/plugin-boot-master-off.php`, whose own `function_exists` guards would go dark if `wp-stubs.php` claimed those names, so suites that need to watch hook registration own them namespace-locally too. `Unit/HarnessPerVisitTest.php` pins all of this — the recorder, the per-request token, the multi-row session fixture and the absences.

`Support/setup-io-stubs.php` owns only the namespaced PHP seams `POW\Http\fopen`, `POW\Http\header` and `POW\Cxml\libxml_use_internal_errors`. They record body-stream opens, response headers and DOM parsing starts while `pow_test_setup_io` is set; otherwise they delegate to native PHP. `SetupEdgeLimitTest` runs the real endpoint, parser, registry and limiters with an audit recorder and a database fixture. It proves the exact edge threshold, early rejection before method/body/parser/archive/lookup and bound-login resolution, downstream budget preservation, per-IP isolation and HTTP-200/cXML-550 emission. Its authenticated-path seam is the connection's bound customer account, whose capability reads are counted through a double: no user is created, found by identity or renamed anywhere in that path, so a connection with no usable account is refused with `setup_no_login` and a connection already holding `Store::MAX_OPEN_VISITS` open visits with `setup_visit_cap`. Its database fixture is a row set, so the per-connection cap and the per-identity supersede are exercised against many visits of one account. It does not prove routing, real HTTP transport or user/session persistence.

The shared transient stub records every expiration passed to `set_transient` in `pow_test_transient_expirations`, alongside the existing value store. Limiter tests execute the default setter and assert 60-second/3600-second TTLs and separate window keys; expiry, cache eviction and concurrency are not simulated.

`Support/quote-doubles.php` holds the four service doubles a `QuoteOrder` is constructed with (`QuoteOrderTestStore`, `QuoteOrderTestLog`, `QuoteOrderTestSettings`, `QuoteOrderTestLogger`) plus `QuoteOrderExplodingCustomer`, a saved shipping address that throws: the saved-customer candidate is the last mutable step a legacy Quote takes between its order row existing and its meta being written, so it is how two suites make construction fail part-way through a saved order now that `pow_quote_shipping_address` is gone. Multiple suites share them, and the standalone runner requires each test file only when it reaches it — doubles declared inside one test file do not exist yet for the file that sorts before it. It extends plugin classes, so the bootstrap loads it after the autoloader.

`Support/visit-key-database.php` supplies the second database boundary fixture, over the tables one visit touches: its punchout session row, its own WooCommerce session row, its connection row and the audit log. It parses the WHERE clause the production SQL carries — row id, `partner_id`, `user_id`, the quoted token/key/identity-hash columns with or without `BINARY`, the unbound-token and NULL-key clauses, the status list and the expiry comparisons — so a query that drops a predicate stops matching instead of answering with whichever row sorts first. `SessionKeyTest` uses it for the key's own Store queries and `StartEndpointTest` for the StartPage redeem, which runs the real `Store`, `Registry` and audit writer and proves that each visit gets its own login token, auth cookie and 32-character cart key. `StartEndpointTest` also owns namespace-local `POW\Http` seams for `wp_generate_password`, `add_filter`, `remove_filter`, `wp_set_auth_cookie` and `wp_safe_redirect`; only `StartEndpoint` calls those inside that namespace.

`CancelAndReturnTest` executes the real return endpoint (Cancel and return, the one thing `/punchout/return` does since 0.5.0), builder, templates, audit writer and session Store: the empty message and the Not sent state, this login's teardown only, the repeat of a double click, the leave question, the Session ended state, and what never transitions. `CheckoutSubmissionTest`, `CheckoutHandoffTest`, `CheckoutLateSubmitTest`, `CheckoutLifecycleTest`, `CheckoutProvenanceTest`, `CheckoutVisitAccountTest`, `PaymentMethodTest`, `OrderMessageTest` and `CheckoutHandoffStateTest` cover the checkout path the same way. `Support/return-database.php` supplies the database boundary fixture, including conditional SQL outcomes. Its session table is a row **set**: `$sessions` is keyed by session id, `$session` is an alias of the first visit (id 42) so single-visit suites read unchanged, and `add_visit()` adds a further visit of the same account — same `user_id`, its own id, login token and per-visit `wc_session_key`, which it refuses to let collide. A lookup naming `wp_session_token` or `wc_session_key` is answered by the row carrying the requested value or by no row at all, and a re-read by row id is answered by the row that id names, so a two-visit fixture cannot silently answer with the wrong basket. The guarded-transition branch (`DeliveryReturnTransitionTest`, kept for the snapshot columns visits returned before 0.5.0 still carry) asserts the **exact** predicate set each transition must carry and throws on any deviation. The Woo stub exposes save/note callbacks and product/item/property rejection results; the WordPress stub records token destruction, cookie clearing and mail attempts. These prove plugin behavior at those boundaries, not native database concurrency, browser cookie policy or Woo persistence. Separate private WordPress/Woo/MariaDB HTTP runs are recorded in the local integration report; their fixtures, paths and captured mail are not distributed with this repository. `ReviewRetirementTest` is the standing check that the review path stays retired: its files absent, nothing shipped naming them, the retired settings kept as stored, the changelog listing every retired setting and shortcode, no current document keeping the retired rule that checkout was refused in a visit, and the test fixtures neutral.

`CartGuardTest` runs the registered seed callback between simulated cart restoration and form addition, checking the resulting contents rather than an exact priority number. It covers persisted-latch reuse on a later request, no-cart deferral, unresolved/ordinary logins, edit/inspect sessions, and a false latch write stopping the request with a retryable 503 before additions can be accepted. `Support/cart-hooks.php` owns only the `POW\Cart` hook-registration and fatal-response seams; the existing shared stubs are unchanged. These are unit boundaries, not native Woo cart persistence. The separate private HTTP regression boots actual WordPress/WooCommerce once per request, using authenticated cookies, native cart restoration and `WC_Form_Handler::add_to_cart_action`, followed by later-request readback. It also checks guest-cart preservation during native token redemption and a REST-shaped request where Woo does not initialize a cart. This does not prove browser rendering, public rewrites, redirects, SameSite behavior or concurrent cart initialization.

`Settings`, `Logger`, `Sessions\Store` and `Audit\Log` are deliberately **not** `final`: a service a WordPress-free suite must double cannot be sealed, and a `final` keyword that only exists to block a test double is a testability defect rather than a design rule. No method of theirs is overridden in production.

## Running

With PHPUnit (>= 10) available:

```bash
phpunit -c phpunit.xml.dist
```

Without PHPUnit or Composer (any PHP >= 8.2 CLI — e.g. straight on the server):

```bash
php tests/run-tests.php
```

The standalone runner uses a minimal PHPUnit-compatible `TestCase` shim (`tests/Support/testcase-shim.php`). `tests/bootstrap.php` loads it only when PHPUnit's own `TestCase` cannot be autoloaded; the check lives there, not in the shim, because PHP declares a file's top-level classes when it compiles the file, before any check inside it runs. The same test files then run under both; PHPUnit 10.5 and 11.5 were checked. Under real PHPUnit a test class must not declare a method PHPUnit's `TestCase` has as final (`run()`, for example), and every test must make at least one assertion or PHPUnit reports it as risky.

Cart block integration has separate PHP and JavaScript checks. Run both from the repository root alongside the unit suite; they use PHP and Node's built-in test runner without installing packages:

```bash
php tests/CartBlocks/surface.php
node --test tests/CartBlocks/cart-blocks.test.js
```

These checks exercise the cart region's own decisions (is this request inside a live visit, and is the connection still active), script dependencies and WooCommerce's public button-filter contract. A real browser must also verify the hydrated Cart block and subsequent cart updates; passing the isolated checks does not establish that behavior.

## Native visits and concurrency

A connection has ONE bound WooCommerce customer account and the plugin creates no users, so two employees shopping at the same moment are the same WordPress user holding two session rows, two `WP_Session_Tokens` entries, two per-visit `wc_session_key`s and two `wp_woocommerce_sessions` rows. Nothing about that can be proved by comparing user ids, and most of it cannot be proved in one process at all: the object cache, the static lock map and the request's own session handler are shared. The opt-in scripts under `Integration/` are where it is proved against a real database.

`Support/native-visits.php` is the shared fixture they load — not one of the bootstrap's support files, because it calls into WordPress and WooCommerce and only an opt-in script may require it. `pow_native_open_visit()` writes one live visit of a bound account — its own login token, its own minted cart key, the buyer identity and hash its request named; `pow_native_enter_visit()` makes the current CLI request that visit by installing a real `logged_in` cookie carrying the visit's token, because `wp_get_session_token()` reads the cookie and nothing else and `wp_set_current_user()` alone leaves every resolver answering "no visit"; `pow_native_visit_handler()` builds the plugin's own session handler for the visit (core's `init_session()` would delete a `pow_` row and migrate what survives onto `session_key = '<user id>'`, which is the collision the per-visit key exists to prevent); `pow_native_cart_row()`/`pow_native_cart_value()` read a basket byte-exactly; and `pow_native_forget_visit_memo()` clears `Plugin::current_session()`'s per-request memo, which is correct for a web request and wrong for a script that plays several in one process. No helper creates a buyer: `pow_native_bound_account()` makes an ordinary `customer`, the only kind of login the model has.

`Integration/ConcurrencyNative.php` runs against an explicitly opted-in disposable local WordPress/WooCommerce database and starts independent WP-CLI workers. It verifies four simultaneous setups for one connection opening four visits with four distinct login tokens and four distinct cart keys on the one bound account, each recording the buyer identity hash its request named; a returning buyer identity superseding only its own earlier visit — that visit's login destroyed and its basket row deleted — while every colleague stays live; two baskets written in an interleaved order under one login, where emptying one leaves the other whole; a colleague's StartPage redeem (and WooCommerce's own `wc_last_active` write) between another visit's stage and its commit not refusing that commit; two simultaneous redeems keeping both logins in the one shared `session_tokens` row; same-payload replay, where a duplicate request is made to land in the window between the winner's claim insert and its commit and receives the winner's response byte for byte; the per-connection open-visit cap (`Store::MAX_OPEN_VISITS`), which sweeps this connection's expired-but-open visits before counting, refuses the next punch-in with cXML 500 and a `setup_visit_cap` audit row, and admits one again when a visit closes; a connection with no usable login — unbound, or bound to a privileged account — refused with cXML 500 and `setup_no_login`, creating no claim row and logging no buyer e-mail; the in-flight claim row a second request must never be able to commit or delete, whether it fails authentication or times out on the connection lock; and atomic rate budgets, which are independent of buyers. The claim barrier is a `query` filter that stalls the winner on its second acquisition of the connection lock, so the window is real rather than simulated.

`Integration/VisitLockdownNative.php` covers the shared-login lockdown end to end against real rows: inside a visit, wp-admin, `/wp/v2/users*`, `/wp/v2/application-passwords*`, the account details and orders screens, wp-login.php (except logout) and the Store API checkout are all refused, a colleague's basket cannot be resolved or addressed by a Cart-Token, and a colleague's quote order cannot be read; outside a visit the same bound account keeps every one of those surfaces, which is the half that a user-id test could never get right. It then checks the connection's My Account list against real WooCommerce: a new connection lists only `dashboard`; the connection form, rendered from WooCommerce's live endpoint map, shows WooCommerce's pages first with the dashboard ticked, then the plugin's tab, then `bulkorder` (registered with WooCommerce through `woocommerce_get_query_vars` when nothing on the fixture already does, with the suite's own content action) under the other-plugins group, with the four payment-method rows and the five pages that never open (logout, lost password, order-pay, order-received, the tab) disabled and no row for a single order. With `dashboard,bulkorder` ticked it loads the account page for real: `WP::parse_request()` and the main query with plain permalinks, the guard's two passes, then `woocommerce_account_content()`. Each opening is judged on the rendered HTML, because WooCommerce shows the dashboard for an endpoint without content. It proves both visits open `bulkorder` with its content and the ticked dashboard with the dashboard; orders, account details, a listed page carrying `?orders`, the dashboard carrying `?orders`, `order-pay` and `order-received` stay closed; an unregistered name shows the ticked dashboard and nothing else; the real menu holds the dashboard and `bulkorder`. Ticking orders opens it with its own content, while `order-pay`, `order-received`, `customer-logout`, `lost-password` and `punchout-integration` stay closed although the row names them and leave the menu, and a single order of the shared account stays closed even with `orders,view-order` in the row; a hand-edited row naming payment pages reads back without them and opens neither. A listed endpoint whose content action is missing stays closed and leaves the menu even with the dashboard ticked; content registered after the first pass is judged by the second; a 0.4.5-style row without `dashboard` keeps the dashboard closed; a second, new connection opens its own dashboard and nothing the first one lists. It then renders the connection form as wp-admin does (`is_admin()` true) on a store whose other plugin adds two pages to WooCommerce's map only on the front end and only for a flagged account, and registers a third only as a rewrite endpoint with account content, all three as rewrite endpoints on every request: the form offers all three under the other-plugins group, ticked, calls none of them missing, has the add-by-name box, and still offers the third after it is unticked; in a visit the ticked rewrite-only page opens with its own content. Last, with the dashboard ticked and `default_password_nag` set on the account: the flag reads false in a visit and true for the account holder outside one, the dashboard shows no temporary-password notice or Resend link (a control run without the plugin's filter shows the link), and a request carrying WooCommerce's Resend action with the visit's own valid nonce is refused before WooCommerce handles it. Each real menu is read after clearing the plugin guard's per-request memo, because the whole suite is one request. Finally core's user insert, called inside a visit, returns `empty_data`, writes no user and leaves one `visit_user_create_refused` audit row per request, while an update of the shared account and a creation outside a visit still work. It proves the plugin's own doors, not the web server's — an actual HTTP run is still the only thing that shows the 302 reaching a browser.

`Integration/TwoBuyerNative.php` proves what only a shared login can get wrong, in one script: one connection bound to one ordinary customer account, two authenticated setup requests through the endpoint's own handler in one CLI process (true concurrency is `ConcurrencyNative.php`) with two buyer identities, two redeems, two baskets, then the rows read back — two auth cookies and two login tokens on one account, two `wc_session_key`s and two basket rows, a returning identity superseding its own earlier visit and nobody else's, and two close-outs through the real `/punchout/return` handler (Cancel and return, the empty message), each destroying one login and deleting one basket row while the colleague's visit stays live. It carries the three regressions that only appear once an account is shared: WooCommerce's own `wc_last_active` write and a colleague's StartPage redeem between one visit's basket stage and its commit, and `_woocommerce_load_saved_cart_after_login`, which a visit must neither read, honour nor delete. It ends on the two setup refusals an operator actually meets — the open-visit cap and a connection with no bound account — and on the account itself, which must still be an ordinary customer carrying no plugin user meta at all. The cart return through checkout, the Quote each visit leaves and the cross-visit order fence are the end-to-end driver's (`driver.py`, checkout path and second leg).

The delivery-store, address-provider and delivery-estimate suites retired with the review in 0.5.0 (nothing writes a consent snapshot; `Store::invalidate_delivery()`, the cart commit's clear, is covered by `SessionSafetyNative` and the handler's unit suites). `AccountNative.php` and `Account/native.py` drive the one surviving My Account surface — the read-only setup-XML download — and prove it does not exist inside a visit.

The implementation follows database [GET_LOCK semantics](https://mariadb.com/docs/server/reference/sql-functions/secondary-functions/miscellaneous-functions/get_lock) and WooCommerce's own session storage, whose `wp_woocommerce_sessions` table is keyed on `session_key` alone and nowhere enforces one row per user — which is what makes many baskets on one login possible at all. Ordinary unit stubs do not prove these concurrency properties.

`Unit/NativeSuiteShapeTest.php` is the standing check on these scripts from inside the ordinary suite, since nothing else runs them: no script may name a removed symbol (the provisioner, the buyer role, the identity mutex, the exit policy), every script must still parse, the visit suites must name the per-visit key and must not build core's session handler, and the concurrency, lockdown and account drivers must still cover the surfaces the model closes.

## What is deliberately NOT covered here

Integration behaviour that requires WordPress/WooCommerce or a real buyer tenant: endpoint routing, auto-login cookie mechanics, cart contents, WooCommerce's own checkout and e-mail behaviour, and everything in the staging test matrix of the build scope (§10) — including the D365 certification items (cart-return encoding acceptance, empty-POOM close-out behaviour, SameSite punchback). Those are staging/certification tests, not unit tests.

## Native admin approval and credentials

`Unit/AdminActionsTest.php` and `Admin/doubles.php` exercise the real Admin actions, page, Registry and Registration through recording SQL and WordPress I/O boundaries. `php tests/Admin/run.php` is the focused entry point. The namespaced admin seams own only admin I/O and do not replace shared global test stubs. Every `POW\Admin` seam the eval-loaded `Admin\Page` binds — including `get_users` — lives in `Admin/doubles.php`, so no test file is a dependency of another test file: a suite that needs the admin surface requires the doubles, never a peer's test case. Coverage includes pending preparation and explicit approval, supplier identity/entitlement validation, every admin handler's POST/capability/nonce gates, escaped direct credentials for manual creation/replacement and generated creation/rotation/approval/reset, rotation overlap, reset failure notices, legacy-owner validation and lock order, stale claim checks, owner-ID auditing, legacy plaintext-notice suppression and native message-renderer cache-header replacement. Recorded writes, captured mail and notices are scanned for the generated plaintext. These are unit boundary checks, not native persistence, wire headers or real concurrent transactions.

`Integration/AdminActionsNative.php` is an opt-in CLI script for the coordinator's disposable local WordPress/WooCommerce candidate. It creates neutral users/connections and checks actual admin hook callbacks, native nonce/capability denial, pending preparation/approval, sealed credential persistence, native audit ownership records, captured mail, binding refusals (a missing account, a privileged one, an account carrying a legacy association, an account another connection already names, and an actor claiming its own), the My Account list saved from real checkbox posts (a new connection's `dashboard` default, a payment page refused on a punchout-only connection, a non-list refused, a name typed in the add-by-name box stored and a malformed one refused, an all-unticked list clearing the column), reset token and visit revocation, preservation of company association and an injected SQL failure notice. It captures terminal responses through WordPress's own `wp_die_handler` and redirect filters, intercepts mail before transport, and prints no credentials. It does not delete its fixtures. Execute only with `POW_NATIVE_TESTS=disposable`, WordPress environment type `local`, a capable fixture administrator and the candidate plugin active. Its file header supplies the invocation. Native HTTP no-store/GET behavior, browser rendering and independent-process ownership races remain separate coordinated acceptance checks; merely linting or passing the standalone suite does not establish them.

## End-to-end HTTP driver (tests/E2E/)

`tests/E2E/driver.py` proves a release from the buyer's purchasing system to the cXML it gets back, over real HTTP against a disposable local WordPress/WooCommerce. Python 3 standard library only; opt-in; nothing in the ordinary suites runs it.

One run: `fixture.php` (over WP-CLI) seeds an ordinary customer account with a deliverable shipping address, one active test connection bound to it (ship-to and notes sent, no delivery line, ALL CAPS on) and two priced simple products, all named with a random run id. For the run it also sets the Checkout button label ("Review") and the payment method's place-order label ("Submit") to non-default values and adds one flat-rate method costing 50.00 ("Courier E2E <run>") to the "rest of the world" shipping zone; `retire` puts those settings back and removes that method. The driver serves the site with PHP's built-in server on `127.0.0.1` (`router.php`), fails the run (`site_server_answers`) if the site never accepts connections, starts its own loopback receiver as the buyer's punchback URL, and then:

1. POSTs a PunchOutSetupRequest in the exact one-line shape a Dynamics 365 tenant sends (`ParserTest::test_parses_the_exact_request_shape_a_live_dynamics_tenant_sends`, neutral identities);
2. redeems the StartPage as a browser does: a GET that redirects is a redeem (0.4.22), a page that posts itself back (0.4.23 and later) is submitted by POST, and then the GET must have left the link unused. From 0.4.23 a GET must answer that page (never a redeem), `no-store`, `no-transform`, `noindex`, `X-Frame-Options: DENY` and a strict Content-Security-Policy (`default-src 'none'`, `form-action 'self'`, `frame-ancestors 'none'`, `base-uri 'none'`, nothing `unsafe`) that names the page's inline script and style by their SHA-256 (no other script, style attribute or event handler); a second GET still answers it; the POST then redeems, a second POST from another browser gets 403, and a repeat POST from the same browser is sent to the same landing page;
3. adds both products with `?wc-ajax=add_to_cart` and checks the landing page is inside the visit (`pow-visit`);
4. leaves through WooCommerce's classic checkout (`Run.checkout_path()`, below): the cart's checkout button, the checkout with PunchOut as the only method, Submit, and the GET handoff; every form is read from the page and posted with its own fields and the clicked button only (`forms.py`). `--path review` is refused on a build with the PunchOut payment method (the run records `run_completed` as failed with the reason and retires the seed); it still applies to a 0.4.23 checkout of the repository;
5. reads the handoff page's form, posts it to the receiver as the browser's auto-post would, and checks the posted field equals the page's byte for byte;
6. decodes the cXML and checks it (`poom.py`; exact 1.2.008 DTD through `dtd.php` and `Support/ExactCxmlDtd.php`): `field_is_cxml_base64`, `posted_form_urlencoded`, `doctype_1_2_008`, `valid_against_cxml_1_2_008_dtd`, `payloadID_timestamp`, `header_reversed_identity_only`, `no_shared_secret_in_return` (no element and not the connection's secret anywhere), `deployment_mode_test`, `buyer_cookie_echoed`, `operation_allowed`, one `line <SKU>` per cart line (quantity, ex-tax unit price, currency, `<product id>|<variation id>`), `no_unexpected_lines`, `every_line_has_uom_and_classification`, `no_freight_line` (or `freight_line` when the connection emits one), `total_equals_sum_of_lines`, `ship_to_present`, `delivery_notes_carried`;
7. repeats the Submit with the cookies the browser held before the first answer (a double click) and expects the same handoff;
8. reads back the visit (`returned`, login dead, the browser no longer in it) and its one order (bound account, buyer cookie, lines equal to the cart, Punchout Quote), then disables the run's connection.

### Running it

A disposable fixture needs: WordPress with environment type `local`, WooCommerce, MariaDB, this plugin active with its master switch on, a store base address that is an allowed shipping destination with a shipping method for it, and outbound mail and HTTP blocked (a must-use plugin returning early from `pre_wp_mail` and `pre_http_request`). PHP CLI needs `mysqli` and `dom`. For the 0.5.0 path the checkout page must be a classic `[woocommerce_checkout]` page, and the site needs an address-book plugin with the API the plugin finds by shape (`Addresses\AccountBook`), or the checkout leg stops at `seed_gives_the_account_saved_addresses`.

```bash
F=/path/to/disposable-fixture            # holds site/ (the WordPress root) and wp-cli.phar
export PHP_INI_SCAN_DIR=...              # if mysqli/dom are loaded from extra ini files
python3 tests/E2E/driver.py --wp-path "$F/site" --wp-cli "$F/wp-cli.phar" --link-plugin "$PWD"
```

| Option | Default | Meaning |
|---|---|---|
| `--link-plugin DIR` | none | Point `wp-content/plugins/punchout-woocommerce` (which must be a symlink) at the candidate checkout for this run and put the old link back afterwards, also on failure |
| `--redeem auto\|get\|post` | `auto` | `auto` behaves like a browser; `post` POSTs the StartPage outright; `get` only GETs (0.4.22 and earlier) |
| `--path auto\|review\|checkout` | `auto` | `auto` takes WooCommerce checkout on any build that has the PunchOut payment method (the seed says so) or is 0.5.0 or later, else the review; `review` is refused on a build with the payment method |
| `--url http://127.0.0.1:PORT` | start a server | Use an already running server for `--wp-path` instead |
| `--out DIR` | `<wp-path>/../e2e-runs/run-<id>` | Private run directory (mode 700) |
| `--wait SECONDS` | `20` | How long the site may take to accept connections before the run fails with `site_server_answers` |
| `--wp-user`, `--php` | `1`, `php` | Fixture administrator for WP-CLI; PHP binary |

Each check prints `PASS` or `FAIL`; the exit code is non-zero on any failure. A run that cannot finish (a connection error, a crash, an interrupt) records `run_completed` as failed with the reason, and a cleanup step that fails is recorded as `cleanup <step>`, so `result.json` (`ok`, `passed`, `failed`, `checks`) never shows an empty failure list for a run that did not complete. The run directory keeps the evidence: `setup-request.xml` (secret redacted), `setup-response.xml`, `cart.html`, `checkout.html`, `handoff.html`, `poom.xml`, `checks.json`, `inspect-<case>.json` (`inspect-main.json` for the main visit), `result.json`, `wp-cli.log`, `php-server.log` and, on the 0.5.0 path, `mail.log` and the second leg's pages. `fixture.json` holds the run's generated shared secret: it is mode 600 and must stay outside this repository. The driver refuses any URL that is not `http://127.0.0.1` and prints no secret. The account, the disabled connection, the products, the visit and its order stay in the fixture; only the run's own settings and priced shipping method are put back.

The driver's own decisions are unit-tested without a site: `python3 -m unittest discover -s tests/E2E -p 'test_*.py'` (form submission rules, every cXML check on a neutral DTD-valid sample, the request shape, start-link and checkout handling, the release path, the 0.4.23 start-page checks, and a run against a site that never comes up or hangs up on every request). `Unit/EndToEndDriverShapeTest.php` is the standing check from the PHP suite: the pieces parse, the fixture script refuses anything but an opted-in disposable local WP-CLI run and creates no user except the ordinary bound customer, the driver targets the loopback address and never prints the secret, and `dtd.php` accepts the plugin's own sample return and refuses a broken one.

What it does not prove: anything a real browser or theme adds (scripts, layout; `browser.py` below covers the start page's script and the checkout with WooCommerce's own script in the fixture's theme), the e-mails' delivery or content (the fixture blocks mail; `mail.log` records which WooCommerce e-mails were sent), concurrency beyond the two racing Submits below (`Integration/ConcurrencyNative.php`), WooCommerce's cron (the unpaid-order clean-up is asked through its own filter, not run), or acceptance by a real purchasing system.

The router (`router.php`) is a test harness as well as a rewrite-less web server. With `POW_E2E_MAIL_LOG` set (the driver sets it for the server it starts) it records each WooCommerce e-mail the site sends, or tries to while the fixture blocks mail, as one JSON line (`{"id": <e-mail id>, "order": <order id>}`) in the run's `mail.log`. A request carrying `X-Pow-E2E-Currency: <ISO code>` is priced in that currency, as a currency switcher would price it; one carrying `X-Pow-E2E-Pause: <1-10>` waits that many seconds after WooCommerce has created its order, so a second Submit can overtake it in a fixed order. All three are WordPress hooks the router builds before WordPress loads; nothing is added to the fixture.

### Real-browser run (tests/E2E/browser.py)

`tests/E2E/browser.py` drives headless Chromium through Python Playwright on the same fixture (0.4.23 and later). It never downloads a browser: name a local Chromium with `--chromium` (or `POW_E2E_CHROMIUM`). It seeds and retires exactly as the driver does, serves the site the same way, and checks:

1. **auto**: Chromium opens a fresh start link; the page's own script posts it once with no Content-Security-Policy violation; the browser lands on the landing page inside the visit (`pow-visit`, signed in), and `inspect` reads the visit as active with a live login. The same browser posting the link again (its own cookies) gets a 302 to the same landing page; a new browser gets 403.
2. **double click**: the fixture step `start_click` turns on **Login link needs a click** for this case (the seed records the setting and retire puts it back); the page waits for a press, a person's double click (two presses 80 ms apart, the second while the first POST is on its way) sends one POST and lands inside the visit, and Back plus one more press lands again.
3. **checkout** (0.5.0): in the first browser both products are added, the classic cart's button (the Checkout button label, "Review") opens the checkout, which offers PunchOut and nothing else with the place-order label ("Submit"); WooCommerce's own checkout script runs, so the ship-to box is ticked again by a click (the one case the HTTP driver cannot drive), a saved shipping entry is chosen from the address book's select and its fields read as the script fills them, and Submit is pressed. The browser lands on the Sent state inside the theme (the handoff posted the cart on the way), the receiver has exactly one cXML carrying the chosen entry as ShipTo, and `inspect` reads the visit as returned with one order whose shipping address is the chosen entry.

`router.php` serves static files reached through the plugin's symlink (the candidate's own scripts and styles; never a path with a dot segment), so the plugin's scripts, the Cart block script and WooCommerce's checkout script run in the browser. Against an export of 57197be (before the 0.4.23 fixes) the same run fails four checks: the same-browser repeat POST (403), the double click (two POSTs, left on the expired page) and Back and press again (403).

```bash
python3 tests/E2E/browser.py --wp-path "$F/site" --wp-cli "$F/wp-cli.phar" --chromium /path/to/chrome --link-plugin "$PWD"
```

Options are the driver's (`--url`, `--out`, `--wait`, `--wp-user`, `--php`); evidence goes to `<wp-path>/../e2e-runs/browser-<id>` (`landing-*.html`, `checkout-browser.html`, `sent-browser.html`, `poom-browser.xml`, `inspect-*.json`, `result.json`). The double-click visit is left open (no Submit) and expires on its own. Its pure parts are unit-tested in `test_browser.py`.

### The 0.5.0 checkout path

`Run.checkout_path()` leaves through WooCommerce's classic checkout (`--path checkout`; `auto` takes it from 0.5.0). The seed sets the Checkout button label ("Review") and the PunchOut payment method's place-order label ("Submit") to non-default values, and makes sure one page draws the classic cart (`[woocommerce_cart]`, slug `pow-e2e-classic-cart`, left in place) whatever the shop's own cart page is; retire puts both settings back. The leg checks: the Cart widget's checkout button (from the add-to-cart fragments) and the classic cart's proceed button carry the label (`cart_widget_checkout_button_carries_the_label`, `cart_checkout_button_carries_the_label`); that button opens the classic checkout inside the visit; `punchout` is the only payment method offered and carries the place-order label, which the button already shows (`checkout_findings`); the form, serialised as WooCommerce's script sends it with the note and `payment_method=punchout` (`checkout_submission`), POSTed to `?wc-ajax=checkout` answers `success` with an address under `/punchout/` (`checkout_answer`); that GET handoff answers with no-store and no-referrer. After the shared capture and cXML checks it fetches the handoff again with the cookies the browser held before the first fetch and expects no form (`the_handoff_is_served_once`), then checks the order: Punchout Quote, placed with the `punchout` method, named by the visit, the buyer's note kept, and the cXML lines equal to the order's lines (`order_lines_match`: quantity, and the ex-tax line total over the quantity as the unit price). A file is the checkout attachment plugin's and the delivery amount on the page is the theme's: neither is the plugin's to prove.

**Checkout in a visit (ticket 76).** When the site has an address-book API (found by shape, as the plugin finds it), the seed gives the bound account saved addresses: reading each book makes the account's own billing and shipping address its default entry, and a second, named shipping entry ("Depot", 2 Depot Road) is added. It records the account's profile as checkout could change it (every `billing_` and `shipping_` user meta value, every address-book meta value, the first and last name, the display name and e-mail). For the run it sets **Shipping destination** to the customer's shipping address (the shipping section opens ticked, as the launch store has it), turns the cheque method on (so "only PunchOut in a visit, never PunchOut outside one" is tested against a real alternative), and makes sure one page carries `[punchout_cart_exits]` and the retired `[punchout_return_button]` (slug `pow-e2e-cart-exits`, left in place); retire puts both settings back. The leg checks: the classic cart has no return button (`the_cart_has_no_return_button`); on the cart-exits page the complete cart control is WooCommerce's checkout link with the Checkout button label and the return button draws nothing (`cart_exits_findings`); the buyer types another billing address (`?wc-ajax=update_order_review`, as WooCommerce's script posts it, `order_review_update`) and opens checkout again, and billing still opens on the account's saved billing profile (`billing_opens_on_the_accounts_saved_billing_profile`, `billing_findings`); the address-book select offers the saved entries on the default (`checkout_offers_the_saved_addresses_on_the_default`, found by the entries it offers, never by its name: `address_book_select`) and the shipping section opens ticked on the default saved address. The buyer chooses the other saved entry, its fields filled as the address book's script fills them (`address_choice`), and Submits. Then: `ship_to_present` and `ship_to_is_the_chosen_saved_address_not_billing` on the cXML, `order_ships_to_the_chosen_saved_address`, and `the_bound_accounts_profile_and_saved_addresses_are_unchanged` (`profile_changes` names any difference); at the end of the run, `after_every_case_the_bound_account_is_unchanged`.

**What the connection screen sets (schema 10, ticket 75).** The seed first runs the linked build's schema upgrade (`Installer::maybe_upgrade()`, as a wp-admin page load would; WP-CLI and the front end never do) and refuses to go on unless the schema version is the build's. The connection then sends each line's name and short description (`line_description` = `name_short_description`) and "Order details sent": the entries the driver's `--checkout-extras` name, then two of the fixture's own, a key WooCommerce's classic checkout writes on every order (`is_vat_exempt`, sent as "Exempt: no") and a key no order has (sends nothing). The first product's short description is markup with entities and odd whitespace; the second only repeats its name in other capitals, so it must be left out. The leg checks `seed_sets_the_line_description_and_the_order_details`, posts the extras' fields with the run's delivery date, and adds these cXML checks (`checkout_expected`): `description <SKU>` (the Description text and the ShortName, in capitals for the all-caps connection), `delivery_instructions_exact` (every merchandise line carries exactly the note, then each detail as "Label: value", joined by " | "; the freight line carries none) and, with `--send-delivery-cost`, `freight_line` at the priced method's 50.00 and `freight_description` (the method's title with the estimate sentence, which then also leads the instructions). Without it, `no_freight_line`. `inspect.json` keeps each order detail's meta value as the order holds it.

`--checkout-extras FILE` is a JSON file kept with the fixture, never in this repository, so the repository names no other plugin: `{"date_offset_days": 7, "fields": {"<field>": "<template>"}, "order_details": [{"meta_key": "...", "label": "...", "format": "text" | "unix_date"}], "instructions": ["<template>"], "uploads": [...], "account_writes": [...]}`. A template may hold `{date:<strftime format>}`; the date is `date_offset_days` (at least 2) after today in UTC, moved to Monday when it falls on a weekend. A field the checkout page does not draw stops the run (`checkout_draws_the_extras_fields`). For a delivery-date plugin that posts a display date and a hidden `dd-mm-yyyy` date and stores a midnight-UTC timestamp, the fields name both inputs, the order detail is that timestamp key with `unix_date`, and the instruction is `"<label>: {date:%Y-%m-%d}"`.

Two more lists (pre-install review, 11 October). `"uploads": [{"settings": "<inline settings object>", "name": "<plain file name>", "content": "<text>", "type": "<media type>"}]` names a file a checkout plugin takes by AJAX before the order is placed: the driver reads the named settings object from the checkout page (as `wp_localize_script` writes it, holding `endpoint` and `nonce`), posts the file to that endpoint from the visit's own browser (`the_file_uploads_before_submit`), and, with the plugin's plain file-name key among the order details and `"<label>: <name>"` among the instructions, proves the name reaches DeliveryInstructions and stays on the order (`the_order_keeps_the_uploaded_file_name_under_an_order_details_key`). `"account_writes": [{"settings": "<inline settings object>", "nonce": "<its key>", "action": "<admin-ajax action>", "fields": {"<field>": "<value>"}}]` names what another plugin lets the signed-in account change on the account (an address book's delete and make-default actions); `{chosen}` and `{default}` in a value name the account's saved shipping entries. Each is posted to `admin-ajax.php` from inside the visit with the nonce the checkout page carries, and the run proves the account's profile and saved addresses are unchanged (`an_account_write_from_inside_the_visit_changes_nothing`) and the refusal audited as `visit_account_write_refused` (`the_refused_account_write_is_audited`); `inspect.json` carries the visit's audit rows counted by event. The handoff and Cancel and return's Not sent page are also checked for `X-Frame-Options: DENY` and a strict Content-Security-Policy that names their own inline script and styles by hash and lets the form post only to the receiver's origin (`handoff_policy_findings`).

| Option | Default | Meaning |
|---|---|---|
| `--checkout-extras FILE` | none | The fixture's own checkout fields, the order details they add, the DeliveryInstructions text they must send, the uploads before Submit and the account writes to refuse (`load_extras`) |
| `--send-delivery-cost` | off | Seed the connection with Send delivery cost on and choose the priced method at checkout, so the freight line and the estimate sentence are checked |

### The 0.5.0 order lifecycle (second leg)

For the order lifecycle the seed also keeps stock on the products (100 each, so checkout holds stock for each order), adds a third product with no SKU, and a 100% coupon with a usage limit (so checkout holds the coupon for each order, and a cart can total zero); retire moves the coupon to the bin. On the main visit the leg checks that the checkout answer does not clear the login cookie (`the_checkout_answer_keeps_the_login_cookie`), and, after the handoff, that a Submit from the browser as the handoff left it (no login cookie) and from the browser as the checkout answer left it (its ended login cookie) each reach the Sent state with no form and post nothing (`a_submit_after_the_handoff_reaches_the_sent_state`, `a_submit_with_the_ended_login_cookie_reaches_the_sent_state`, `a_submit_after_the_return_posts_nothing_again`); its order holds no stock or coupon and WooCommerce's unpaid-order filter would not cancel it. Then three visits of their own, each check prefixed with its case:

- `race:` two Submits from one visit, the first paused after WooCommerce created its order: the second gets the handoff, the first reaches the Sent state; one handoff and one post; one Punchout Quote, named by the visit; the overtaken order is in the bin with its holds released.
- `zero:` the coupon brings the cart to zero (free shipping chosen): PunchOut is still the only method offered; a Submit priced in another currency is refused before any order exists and leaves the visit open; the Submit then hands off a DTD-valid cXML with lines at 0.00, the order is a zero-total Punchout Quote with stock and coupon holds released, and a note past 2,000 characters reaches DeliveryInstructions cleaned and shortened, so that with the order details after it (and the estimate sentence before it, when delivery cost is sent) the whole fits within 2,000 (`instructions_fit`). With `--send-delivery-cost` the free shipping line is the freight line, at 0.00.
- `sku:` a cart holding the product with no SKU is refused, naming it, before any order exists; nothing is posted and the visit stays open.
- `pending:` (ticket 76) a Submit paused after WooCommerce created its order, before the payment method runs: the pending order is already found by its visit (provenance stamped as checkout creates it), and the visit can open neither order-received nor order-pay for it (each a redirect to the landing page). The buyer typed a one-off delivery address (the address-book choice that is not a saved entry): once the Submit completes and hands off, ShipTo and the Quote carry it, and the account's profile and saved addresses are unchanged.
- `refuse:` (ticket 76) in a visit: the cheque method forced into the posted form is refused with PunchOut's own message; the Store API checkout (`?rest_route=/wc/store/v1/checkout`, with the Store API nonce) answers 403 `pow_requisition_only`; the main visit's Quote is refused at order-pay and order-received; nothing is ordered or posted and the visit stays open. Then a guest (outside any visit): checkout offers the cheque method and never PunchOut; a forged `payment_method=punchout` with a complete billing and shipping address is refused with PunchOut's own message and creates no order (counted by its billing e-mail, `POW_E2E_GUEST_EMAIL` for `inspect`); the Quote's order-pay page never opens; and the cart-exits control is WooCommerce's own "Proceed to checkout" link.

### The 0.5.0 state page and asking before leaving (ticket 77)

On the main visit the leg also checks that the plain page that posts the cart is the Sending state (`the_handoff_page_is_the_sending_state`). After the second leg, the fixture step `states` makes sure one page draws `[punchout_state sent_title="Sent (e2e)" button_url="/"]` (slug `pow-e2e-state`) and one draws `[punchout_abandon_button question="Leave without sending (e2e)?"]` (slug `pow-e2e-leave`), both left in place, chooses the first as the state page and turns **Ask before leaving** on with non-default labels; the seed records each setting as it was and retire puts it back. The step `end_visit` ends a visit as logout, the clean-up and the master switch do (`Store::expire_and_destroy()`). Then, each case in a visit of its own and prefixed `states:`:

- **Sending and Sent:** the page that posts the cart has `pow-state--sending`, its form is `pow-state__actions` and its button is the state page button label; fetched again it answers a redirect to Sent on the state page, which is drawn inside the theme (the body class names the page), not stored, indexed or sniffed, gives away no referrer, shows the attribute's title and the setting's button; a late Submit reaches the same Sent; one post in all (`state_findings`, `state_location`).
- **Link expired:** the used start link, posted again from another browser, is redirected to Link expired.
- **Session ended:** after `end_visit`, Cancel and return is redirected to Session ended, and so is the next page, whose answer also clears the dead login cookie; the page after is an ordinary guest page.
- **Asking first and Not sent:** with a line in the cart the cancel control names a closed dialog with the question attribute, the two button labels and the plugin's script (`leave_controls`); posted without a script it is sent back to its page with `?pow_leave=ask`, nothing is posted and the visit stays open; that page draws the dialog open; the dialog's answer leaves with the plain Not sent page, which posts an empty PunchOutOrderMessage; the visit is closed with no order; a browser still holding the cookie is sent to Not sent on the state page.
- **An empty cart** draws no dialog and leaves at once.

The real-browser run adds two cases after the start-link and checkout cases: **states** (a used start link opened in another Chromium lands on Link expired drawn in the theme; after `end_visit` the next page lands on Session ended, signed out, and the page after is ordinary) and **leave** (pressing Cancel and return opens the question as a modal dialog with Keep shopping focused and sends nothing; Keep shopping closes it and the visit stays open; the leave button answers with the Not sent page, which posts one empty message, and the visit is closed).

Last, from `mail.log`: exactly one e-mail per Punchout Quote, the Quote e-mail (`pow_quote_received`); none for the binned or refused orders; no failed or cancelled order e-mail anywhere in the run; and each product's stock is still 100 (a Punchout Quote moves none).
