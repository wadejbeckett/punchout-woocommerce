# Delivery and confirmation

## Current behavior

The local 0.4.0 build keeps ordinary shopping and an editable cart, then requires review of products, destination, available shipping and notes before every physical cart return. The final button is **Submit**, with **Back to cart** before final submission. There is no payment step: checkout is not available inside a punchout visit. The button returns the basket to the purchasing workflow; it does not approve a requisition itself.

**The review's words (0.4.23).** Settings → PunchOut: **Review Submit button** (default "Submit"), **Review items heading** (default "Items") and **Review total label** (default "Total"); the filters `punchout_review_submit_label`, `punchout_review_items_heading` and `punchout_review_total_label` run last, and a blank result keeps the default. The page says what the button does ("Sends this cart to your purchasing system.") and says nothing about approval. When the connection does not send the delivery line (`emit_delivery_line` off), the summary is one row, the total label with the merchandise amount: no delivery estimate, no estimate note and no tax sentence. With the delivery line on, the summary keeps Merchandise, Delivery estimate and the total, and one sentence, "Amounts exclude tax.".

Store administrators maintain each connection's enabled addresses at **WooCommerce → PunchOut**, or, since 0.4.15, in the connection account's own saved addresses when the site has an address-book API (see [The account's saved addresses](#the-accounts-saved-addresses-0415)). Every punchout visit selects from that connection's entries. A visit cannot edit or remove entries, and may only add a new one when the connection allows it (see [Buyer-added delivery addresses](#buyer-added-delivery-addresses-048)); there is no owner-facing address screen. Two visits on the same store account choose independently: a selection made in one visit is not the other's. Core storage and shipping use WordPress/WooCommerce, without an address-book plugin. Preserve a valid selected shipping method, otherwise use Woo's configured default. Distinguish free delivery, pickup and unavailable rates. No available rate must not silently become free shipping.

Confirmation preserves an immutable address, code, method, charges and notes snapshot, and the optional preferred delivery date, bound to the visit that made it. Changing the cart, destination or accepted rates requires renewed confirmation, and a confirmation from one visit can never be spent by another. When optional freight export is enabled and a rate is available, freight appears once with matching Quote and cXML totals.

## Three address authorities

| Message/stage | Meaning |
|---|---|
| Incoming setup ShipTo | Buyer-supplied shopping context or candidate destination. |
| Supplier confirmation/outgoing ShipTo | Supplier's accepted destination snapshot and optional reference. |
| Final purchase order | Authorized purchasing instruction requiring reconciliation before fulfilment. |

Address codes identify data; they are not individual endpoint URLs. Outgoing address/reference emission and freight ItemIn are separate options, off by default and constrained by the declared dialect. An absent field can therefore mean the relevant connection option is off or the receiver dialect does not support it.

For Dynamics, `PUNCHOUTSHIPTO` supplies legal-entity context; `PUNCHOUTSHIPTOUSER` can substitute the user's address. PO properties such as `DELIVERTO` and fixed address IDs apply to different message stages. Microsoft's [enhancements reference](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/purchasing-cxml-enhancements#set-the-order-properties) explains them. It does not prove a tenant will import supplier-selected addresses or accept freight lines.

## The account's saved addresses (0.4.15)

WooCommerce keeps one shipping address per customer. A site that wants several per account installs an address-book extension; PunchOut reads that book for the connection's own account and offers those addresses on the review page, the account's default first. Nothing names a product: the plugin looks for a PHP function called `get_address_book` (in any namespace) whose first parameter is a `WC_Customer` and whose second is the type, returning an object with `addresses()` (key → array of unprefixed WooCommerce address fields, optionally `address_nickname`) and `default_key()`. The filter `punchout_address_book_function` can name the callable directly. Without such a function, or while the account holds no address that passes the store's own country rules, the company book stays the store; `add_filter( 'punchout_address_provider', fn() => 'company' )` pins the company book on a site that has the API but does not want it used.

- **Labels.** The saved nickname; else the company; else "street, city".
- **Codes.** Address-book extensions hand out keys like `a1`, `a2` and reuse a key once its address is deleted, so PunchOut keeps its own map per connection on the account (user meta `_pow_account_codes_{connection id}`: key → {code, fingerprint of the address}, plus the claims of every code ever issued). A key whose address changed gets the next code from the connection's delivery code prefix and the old code is retired for good; with an empty prefix codes are empty and only the fingerprint moves. The map is reconciled whenever the addresses are read for a review.
- **Selection.** Choices carry `provider: account`, `source: account_book`, `book_revision: null` and `entry_fingerprint` (key, label, address, code). A stored selection is checked against the account's current address under that key on every review and at the return; a changed address, label or code answers "The selected address changed. Review and confirm it again.", a deleted one "The selected address is no longer available."
- **Maintenance.** Store staff maintain the account's addresses in the extension's own screens (for example by signing in as the account, or through its REST routes). The company book editor at WooCommerce → PunchOut keeps working but is not offered to visits while the account has addresses. Buyer-added addresses (0.4.8) write the company book and are therefore not offered either.
- **Migration.** `wp punchout migrate-addresses <connection-id> --dry-run`, then without the flag: every enabled company-book entry is copied into the account's saved addresses (nickname = label; the first copied entry becomes the default when the account had none) and its code is written into the map. Entries whose address the account already holds are skipped, so the command can be rerun. The company book is left untouched; remove its entries afterwards if the site no longer wants them. Audit event `address_book_migrated`.
- **Rollback.** 0.4.14 and earlier do not know `provider: account`: an open visit that selected an account address must review again after a rollback; the map and the extension's addresses are left alone.

## Preferred delivery date, collection and delivery periods

**Attachment (0.4.14).** The review page offers one optional file beside the delivery notes. Settings → PunchOut: **Attachment field** (on by default), **Attachment label** (default "Attachment") and **Attachment help text** (default "Optional: a sheet or document for this order."); the filters `punchout_attachment_enabled`, `punchout_attachment_label`, `punchout_attachment_help`, `punchout_attachment_types` (default `xlsx, xls, csv, pdf, png, jpg, jpeg, gif, webp`) and `punchout_attachment_max_bytes` (default 10 MB; PHP's own upload limit applies when lower) run last. A file is checked by extension, by its bytes (WordPress's file-type check) and by size; a refused file is reported in plain words beside the notes, and the notes and preferred date the buyer typed are kept. An accepted file is moved to `uploads/punchout-woocommerce/attachments/<32 random hex>/<name>` (directories 0700, `.htaccess` deny and an index file on the parent: it is never reachable by URL) and remembered in the visit's own WooCommerce session: it survives **Update delivery options** and a refused submit, shows as "Attached: name (size)" with a **Remove it** tick, and choosing another file replaces it. When the cart returns and the Punchout Quote order is created, the pending file is claimed by that order (before the e-mail): meta `_pow_attachment` (`{id, name, size, type, attached_at}`), an order note "Buyer attachment: …", an **Attachment** line under the shipping address on the order screen with a download link, and an **Attachment** line with the same link in the "PunchOut order received" e-mail. Downloads go through `admin-post.php?action=pow_attachment&order=…&id=…` and need a signed-in user with `manage_woocommerce`; the order-screen link also carries a nonce. The file is never sent to the purchasing system. Files whose visit never returned are deleted after two days by the hourly housekeeping job. Rollback to 0.4.13 leaves the stored files and meta in place and simply stops offering the field.

**Reply-To (0.4.14).** The "PunchOut order received" e-mail has a Reply-To setting under WooCommerce → Settings → Emails. A valid address replaces WooCommerce's sender Reply-to header; blank keeps the sender.

**The store is told (0.4.13).** When the Punchout Quote order is created, the "PunchOut order received" e-mail (WooCommerce → Settings → Emails) goes to its configured recipients, comma-separated, defaulting to the store's admin address. It carries the WooCommerce order details, the delivery address and code, the preferred date, the buyer's notes and identity, and a link to the order. WooCommerce's own "New order" e-mail does not fire for this status.

**Inside the theme (0.4.12).** A GET of `/punchout/confirm` is drawn inside the active theme's header and footer (`get_header()`/`get_footer()` at `template_redirect`, status 200, title "Review your cart", body class `pow-confirmation-page`, stylesheet enqueued). The forms post to the same route and keep the plain no-store document. Block themes, and sites that return false from the `punchout_review_in_theme` filter, keep the plain document for GET as well.

**Preferred delivery date.** The review page has an optional native date field for physical carts. It defaults to 14 days ahead, and its minimum is tomorrow, both in the site timezone (Settings → General). The minimum is checked when the buyer reviews and confirms, not at return, so consent given before midnight still returns after it. An emptied field means no preference. A date that fails these checks on **Update delivery options** still lets the chosen address and method apply; the review shows the date error, keeps the refused date in the field (for display only; it binds nothing) and **Submit** stays disabled until the date is fixed or emptied. A virtual-only cart never stores a date. The date is stored in confirmation schema 2 and bound to the stored cart fingerprint but not the review digest, so the buyer can change it without pressing **Update delivery options**. On the Quote it is stamped as `_pow_preferred_delivery_date` (only when set), written in the Quote creation note and shown on the admin PunchOut line. It is never sent in the PunchOutOrderMessage. A submit that carries no date field (for example an older template override) stores no preference; only a chosen date is written, as confirmation schema 2. Rollback: 0.4.7 and earlier cannot read a schema-2 confirmation or a Quote that carries a preferred date; dateless confirmations stay schema 1 and survive a rollback.

**Collection.** A cart counts as collection when every selected rate is WooCommerce Local Pickup: `local_pickup` (the zone method), `legacy_local_pickup`, or `pickup_location` (the Blocks Local Pickup method). This is a fixed list and is worked out from the stored `method_id`, not stored separately. The review then calls the method section **Collection**. Collection points or hubs are the store owner's own pickup methods or zones. The buyer still chooses an address, because WooCommerce offers zone pickup based on the destination; when there is only one address it is already selected. Collection with no address at all would put the store's own address in ShipTo and is not supported; that is an open question for the owner.

**Delivery periods.** There is no separate setting. Write the delivery period in the shipping method title, for example `Courier (3–5 working days)`. Keep the title to 190 characters or fewer: the review refuses a longer one. Changing a title changes the stored rate, so open confirmations need a fresh review. The review shows the title beside each method, the Quote creation note carries it (`Delivery method: …` or `Collection: …`), and with `emit_delivery_line` the freight ItemIn Description is the selected title or titles, as plain text joined with `; ` in package order and not uppercased. When a title strips to nothing the Description falls back to `Delivery`.

**Confirmation schema.** Schema 1 records (9 keys) are still read exactly as stored and still return. A new confirmation with a chosen date is schema 2 (10 keys: schema 1 plus `preferred_delivery_date`, a `Y-m-d` string); a new dateless confirmation is written as schema 1. Schema 2 records with a null date, written by earlier 0.4.8 builds, are still read. Each schema's field set is exact.

## Buyer-added delivery addresses (0.4.8)

An administrator can let a connection's buyers add a delivery address themselves. On the connection form at **WooCommerce → PunchOut**, tick **Buyers may add delivery addresses to the company book** (row *Buyer-added addresses*). It is off by default, for new and existing connections.

- **Where.** With the box ticked, the delivery review page (`/punchout/confirm`) of a physical cart shows **Add a delivery address** at the foot of the review, with a link from the address list. It is a section of the review form with its own buttons, so an add also sends the notes and preferred date as typed; the review reads none of the address fields, and the add reads none of the review's other fields. The add buttons skip the browser's check of the review's required fields (the address list, the acknowledgement); the server validates the add.
- **Fields and validation.** An address name (up to 190 characters) and WooCommerce's own shipping fields for the chosen country, the same field set and validation as the administrator's editor. **Update fields for the chosen country** redraws the fields after a country change without saving. There is no code field.
- **What is saved.** A new entry in the connection's company book (stored on the connection's store account, not on the visit), enabled at once and given the next code from the connection's delivery code prefix. Adding the same name and address again (a double-click, or a form sent twice) selects the enabled entry already there and uses no second entry or code. The add answers with a redirect to the review (303), so a browser reload repeats the review, never the add. The review then shows the entry as the selected address, with the notes and preferred date the buyer had typed. The buyer checks the delivery method and presses **Submit** as usual. Adding an address stores no consent; the selection and those two fields wait in the visit's own WooCommerce session until the next review page takes them, once.
- **Audit.** Who added it is recorded in the audit log as `address_book_buyer_added`, with the visit's `session_id`, `buyer_hash` (the first 12 characters of the visit's buyer-identity hash) and `buyer_name` when the purchasing system sent one. The raw e-mail is never logged. The entry itself holds only its name, address, code and enablement: the entry and book shapes are unchanged, so 0.4.7 still reads the book after a rollback.
- **Limit.** A buyer can add entries until the book holds 100; after that the buyer is asked to contact the company administrator. The administrator's editor has no such limit.
- **Add only.** Buyers never change, disable or remove entries. That stays with the administrator.
- **Other open reviews.** An add raises the book's revision, so another open review of the same connection must press **Update delivery options** once (it shows *Delivery changed…*). Consent already stored is not affected.
- **Authorisation.** The add is checked again under the connection lock: the box must still be ticked, the connection active, and the request must come from that same active visit on its own basket. A forged add request to a connection without the box ticked gets the expired page (403).
