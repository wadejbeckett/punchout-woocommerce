# Delivery and confirmation

## Current behavior

The local 0.4.0 build keeps ordinary shopping and an editable cart, then requires review of products, destination, available shipping and notes before every physical cart return. The final button is **Submit for approval**, with **Back to cart** before final submission. There is no payment step: checkout is not available inside a punchout visit. That label means returning the basket for the purchasing workflow; it does not approve a requisition itself.

Store administrators maintain each connection's enabled addresses at **WooCommerce → PunchOut**. Every punchout visit selects from that connection's entries. A visit cannot edit or remove entries, and may only add a new one when the connection allows it (see [Buyer-added delivery addresses](#buyer-added-delivery-addresses-048)); there is no owner-facing address screen. Two visits on the same store account choose independently: a selection made in one visit is not the other's. Core storage and shipping use WordPress/WooCommerce, without an address-book plugin. Preserve a valid selected shipping method, otherwise use Woo's configured default. Distinguish free delivery, pickup and unavailable rates. No available rate must not silently become free shipping.

Confirmation preserves an immutable address, code, method, charges and notes snapshot, and the optional preferred delivery date, bound to the visit that made it. Changing the cart, destination or accepted rates requires renewed confirmation, and a confirmation from one visit can never be spent by another. When optional freight export is enabled and a rate is available, freight appears once with matching Quote and cXML totals.

## Three address authorities

| Message/stage | Meaning |
|---|---|
| Incoming setup ShipTo | Buyer-supplied shopping context or candidate destination. |
| Supplier confirmation/outgoing ShipTo | Supplier's accepted destination snapshot and optional reference. |
| Final purchase order | Authorized purchasing instruction requiring reconciliation before fulfilment. |

Address codes identify data; they are not individual endpoint URLs. Outgoing address/reference emission and freight ItemIn are separate options, off by default and constrained by the declared dialect. An absent field can therefore mean the relevant connection option is off or the receiver dialect does not support it.

For Dynamics, `PUNCHOUTSHIPTO` supplies legal-entity context; `PUNCHOUTSHIPTOUSER` can substitute the user's address. PO properties such as `DELIVERTO` and fixed address IDs apply to different message stages. Microsoft's [enhancements reference](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/purchasing-cxml-enhancements#set-the-order-properties) explains them. It does not prove a tenant will import supplier-selected addresses or accept freight lines.

## Preferred delivery date, collection and delivery periods

**Preferred delivery date.** The review page has an optional native date field for physical carts. It defaults to 14 days ahead, and its minimum is tomorrow, both in the site timezone (Settings → General). The minimum is checked when the buyer reviews and confirms, not at return, so consent given before midnight still returns after it. An emptied field means no preference. A date that fails these checks on **Update delivery options** still lets the chosen address and method apply; the review shows the date error, keeps the refused date in the field (for display only; it binds nothing) and **Submit** stays disabled until the date is fixed or emptied. A virtual-only cart never stores a date. The date is stored in confirmation schema 2 and bound to the stored cart fingerprint but not the review digest, so the buyer can change it without pressing **Update delivery options**. On the Quote it is stamped as `_pow_preferred_delivery_date` (only when set), written in the Quote creation note and shown on the admin PunchOut line. It is never sent in the PunchOutOrderMessage. A submit that carries no date field (for example an older template override) stores no preference; only a chosen date is written, as confirmation schema 2. Rollback: 0.4.7 and earlier cannot read a schema-2 confirmation or a Quote that carries a preferred date; dateless confirmations stay schema 1 and survive a rollback.

**Collection.** A cart counts as collection when every selected rate is WooCommerce Local Pickup: `local_pickup` (the zone method), `legacy_local_pickup`, or `pickup_location` (the Blocks Local Pickup method). This is a fixed list and is worked out from the stored `method_id`, not stored separately. The review then calls the method section **Collection**. Collection points or hubs are the store owner's own pickup methods or zones. The buyer still chooses an address, because WooCommerce offers zone pickup based on the destination; when there is only one address it is already selected. Collection with no address at all would put the store's own address in ShipTo and is not supported; that is an open question for the owner.

**Delivery periods.** There is no separate setting. Write the delivery period in the shipping method title, for example `Courier (3–5 working days)`. Keep the title to 190 characters or fewer: the review refuses a longer one. Changing a title changes the stored rate, so open confirmations need a fresh review. The review shows the title beside each method, the Quote creation note carries it (`Delivery method: …` or `Collection: …`), and with `emit_delivery_line` the freight ItemIn Description is the selected title or titles, as plain text joined with `; ` in package order and not uppercased. When a title strips to nothing the Description falls back to `Delivery`.

**Confirmation schema.** Schema 1 records (9 keys) are still read exactly as stored and still return. A new confirmation with a chosen date is schema 2 (10 keys: schema 1 plus `preferred_delivery_date`, a `Y-m-d` string); a new dateless confirmation is written as schema 1. Schema 2 records with a null date, written by earlier 0.4.8 builds, are still read. Each schema's field set is exact.

## Buyer-added delivery addresses (0.4.8)

An administrator can let a connection's buyers add a delivery address themselves. On the connection form at **WooCommerce → PunchOut**, tick **Buyers may add delivery addresses to the company book** (row *Buyer-added addresses*). It is off by default, for new and existing connections.

- **Where.** With the box ticked, the delivery review page (`/punchout/confirm`) of a physical cart shows **Add a delivery address** at the foot of the review, with a link from the address list. It is a section of the review form with its own buttons, so an add also sends the notes and preferred date as typed; the review reads none of the address fields, and the add reads none of the review's other fields. The add buttons skip the browser's check of the review's required fields (the address list, the acknowledgement); the server validates the add.
- **Fields and validation.** An address name (up to 190 characters) and WooCommerce's own shipping fields for the chosen country, the same field set and validation as the administrator's editor. **Update fields for the chosen country** redraws the fields after a country change without saving. There is no code field.
- **What is saved.** A new entry in the connection's company book (stored on the connection's store account, not on the visit), enabled at once and given the next code from the connection's delivery code prefix. Adding the same name and address again (a double-click, or a form sent twice) selects the enabled entry already there and uses no second entry or code. The add answers with a redirect to the review (303), so a browser reload repeats the review, never the add. The review then shows the entry as the selected address, with the notes and preferred date the buyer had typed. The buyer checks the delivery method and presses **Submit for approval** as usual. Adding an address stores no consent; the selection and those two fields wait in the visit's own WooCommerce session until the next review page takes them, once.
- **Audit.** Who added it is recorded in the audit log as `address_book_buyer_added`, with the visit's `session_id`, `buyer_hash` (the first 12 characters of the visit's buyer-identity hash) and `buyer_name` when the purchasing system sent one. The raw e-mail is never logged. The entry itself holds only its name, address, code and enablement: the entry and book shapes are unchanged, so 0.4.7 still reads the book after a rollback.
- **Limit.** A buyer can add entries until the book holds 100; after that the buyer is asked to contact the company administrator. The administrator's editor has no such limit.
- **Add only.** Buyers never change, disable or remove entries. That stays with the administrator.
- **Other open reviews.** An add raises the book's revision, so another open review of the same connection must press **Update delivery options** once (it shows *Delivery changed…*). Consent already stored is not affected.
- **Authorisation.** The add is checked again under the connection lock: the box must still be ticked, the connection active, and the request must come from that same active visit on its own basket. A forged add request to a connection without the box ticked gets the expired page (403).
