# Single-login mode — v0.4.0 (breaking)

Confirmed by the owner on 21 September 2026 after grilling. Replaces every earlier variant (per-employee accounts, separate bound-login field, dual exit, front-end self-service). Nothing in an earlier copy of this file, in a ticket packet or in a review note survives where it disagrees with what is written here.

The model and decisions below are the specification. **How the build landed** records what the merged code actually does, and is the section to read before touching the areas it names.

## The rule

The plugin does its whole job on any WordPress site with WooCommerce and nothing else. No site file, no mu-plugin, no hook whose purpose is site glue, no knowledge of any other plugin. Buyers are signed in as the customer's own account and see exactly what that account sees.

## The model

1. **The connection's customer account is the login.** `partners.owner_user_id` (already there) is the account buyers punch in as. No separate binding field, no password flag. It is bound on the connection's own edit screen and cannot be transferred or cleared afterwards. A usable account exists, can `read`, and holds none of `Registry::PRIVILEGED_CAPABILITIES`; the same test refuses the binding, refuses setup and refuses the redeem. A connection with no usable account refuses `PunchOutSetupRequest` with cXML 500, an audit row (`setup_no_login`) and a persistent admin notice.
2. **The plugin never creates, renames or deletes users.** `Buyers\Provisioner`, ephemeral identities, the `punchout_buyer` role, the identity mutex, latest-wins, the dormant-buyer cron and the hooks `pow_buyer_provisioned` / `pow_buyer_deactivated` are removed. No migration tooling.
3. **One WooCommerce session row per visit.** Every setup request gets its own WP auth cookie and `WP_Session_Tokens` entry for the customer account and its own `wp_woocommerce_sessions` row keyed by a per-visit key (`pow_` + 28 hex = 32 chars, UNIQUE in `sessions.wc_session_key`, minted inside `Store::bind_login()`). Two employees at once = one WP user, two visits, two baskets, two delivery selections. The same buyer identity punching in again supersedes only its own earlier visit. Open visits per connection are capped. A visit is a row, not a person: many open rows for one `user_id` is the normal state.
4. **Buyer identity is data.** Name and e-mail from the cXML request (UserEmail → UniqueUsername → UniqueName → Contact/Email; UserPrintableName → UserFullName → User) live on the session row (`buyer_identity`, `buyer_name`, `buyer_identity_hash`; empty allowed) and are stamped on the quote order as meta (`_pow_buyer_identity`, `_pow_buyer_name`, `_pow_buyer_cookie`), an order note and a "Bought by" line on the admin order screen. `customer_id` stays the customer account. No e-mails to buyers.
5. **PunchOut only.** The "PunchOut and checkout" exit, `Checkout\PayExit` and the per-buyer exit policy are removed. Checkout is blocked inside a visit.
6. **Admin-only management.** The front-end application flow and every My Account action are removed. The My Account "Punchout integration" tab keeps only the read-only setup XML download (placeholder secret) for the account holder while the connection is active, and is unreachable during a visit.
7. **Shared-login lockdown.** Inside a visit the request cannot reach wp-admin, `/wp/v2/users*`, application passwords, a My Account page the connection has not ticked (account details and password change included), another visit's basket, or another visit's quote order. Every "is this mine" check compares the per-visit key, never the user id. Every door fails closed: a visit lookup that cannot run answers "in a visit". Since 0.4.5 a connection may list other My Account pages its visits may open, since 0.4.6 as a checkbox list that includes the dashboard, and a visit never creates a user; see **My Account in a visit (0.4.5, 0.4.6)**.

## Decisions on the open points (owner delegated these; do not reopen)

1. Audit log: no new column. Setup rows put `buyer_hash` (sha256 of partner_id|identity, first 12 hex) and `buyer_name` in the detail JSON; never the raw email in the log.
2. Withdrawn. The delivery consent JSON gains no buyer fields: the quote order carries the buyer meta beside the confirmation and the session row carries the identity, so the consent record needs neither. `buyer_user_id` remains the connection's bound account and no longer discriminates; `session_id` remains the key.
3. Open-visit cap per connection: constant `Store::MAX_OPEN_VISITS = 50`, no filter. Expired rows are swept before counting.
4. Raw buyer identity (usually an email) is stored in cleartext on the session row (`buyer_identity`) and on the quote order (`_pow_buyer_identity`) because admins must see who bought; the indexed column is `buyer_identity_hash`.
5. Anonymous visit: no new audit event; `setup_ok` detail carries `buyer: none`.
6. Owner e-mails that belonged to the front-end registration flow go with it. Admin-created connections send nothing. The pending/approve/reset admin lifecycle stays as is (harmless, no producer).
7. `partners.mode` and `partners.exit_policy` columns stay; only `requisition_only` / `punchout_only` are ever written or honoured. Checkout is blocked inside every visit.
8. `[punchout_cart_exits]` keeps rendering the native checkout link for ordinary shoppers outside a visit; inside a visit only the return control renders.
9. `Session::ORDERED` stays as inert vocabulary; nothing writes it after PayExit goes.
10. A fresh visit's customer snapshot is seeded from the bound account's profile address, labelled "Company address" (not "Your current delivery address"); the delivery review still decides.
11. "Bought by" wording. Admin line and order note: `Bought by {name} ({email}) via PunchOut ({connection name})` — parentheses, never angle brackets, because a WooCommerce order note is rendered through `wp_kses_post`, which reads `<{email}>` as an HTML tag and deletes the address; when name is empty use the email alone; when nothing was supplied: `Bought by an unnamed buyer via PunchOut ({connection name}); the purchasing system sent no name or e-mail`. A quote order carrying no `_pow_buyer_*` meta at all — one taken before this release, whose buyer was the order's own customer — gets no line and no note rather than a false claim that the purchasing system named nobody.
12. Tautology guard: a unit test greps `includes/` and fails when `get_customer_id()` appears within three lines of `user_id` or `get_current_user_id()` outside `includes/Cart/SessionKey.php`.
13. `docs/single-login-mode.md` keeps its name.
14. No other plugin is ever named in code, in-plugin strings or these docs; they say "your pricing or visibility plugin".

## How the build landed

One paragraph per area, naming the load-bearing decision a later change has to respect.

**The visit key.** `POW\Cart\SessionKey` mints it: `pow_` plus 28 hex, `SessionKey::LENGTH` 32 characters, self-checked at mint. `is_visit_key()` accepts lowercase hex only and is the shape test; `for_session()` resolves a visit's own basket. `Store::bind_login( id, token, expires, key )` writes the login token and the key in one guarded UPDATE that requires an active row, an unbound token and a NULL key, then reads all four back; `StartEndpoint` retries once with a fresh key, which can only win a UNIQUE collision. Nothing else writes the column — `Store::create()` deliberately leaves it NULL at setup, which is why the column must stay nullable with no default.

**Resolving a visit.** There are two resolvers and they are not interchangeable. `Store::find_for_login( user_id, wp_session_token )` is the login side; its `ORDER BY id DESC LIMIT 1` and its non-BINARY token comparison are both load-bearing (the comparison keeps the `(user_id, wp_session_token)` index in play). `Store::find_by_wc_session_key()` is the basket side. `Sessions\Current::visit()` is the one request-scoped resolver over the login side, and `Plugin::current_session()` memoises only a conclusive answer. A resolver that throws does not mean "no visit" — every caller either propagates or fails closed.

**Setup.** `Buyers\Identity::from_message()` reads the identity and the name; `Identity::hash( partner_id )` is `sha256( partner_id . '|' . identity )` and the full 64 hex goes in `buyer_identity_hash`, while the audit detail carries only the first 12. Supersede is `Store::open_for_identity( partner_id, identity_hash )`, so an anonymous visit supersedes nothing. The cap is enforced once, in `SetupEndpoint::refuse_over_cap()`, inside the connection lock and before the insert; it sweeps this connection's expired-but-open rows first, because another connection's rows belong to another lock. A replay of an existing `(partner_id, payload_id)` returns before the cap is consulted, on purpose: a lost response must stay re-deliverable at the cap.

**Redeem and return.** The StartPage sets the auth cookie directly and never fires `wp_login`, so WooCommerce never writes the saved-cart-after-login flag for a visit. Setup re-proves the bound account inside the connection lock before it commits the visit, and answers 500 if the binding changed under it. The redeem proves it once more: the claim's user must be the connection's own owner, and that account must exist, be able to `read`, hold no privileged capability and carry no legacy `_pow_partner_id` user meta. The return winner guard compares the re-read row's key with the snapshot's, byte-exactly, in addition to the guarded-transition predicates. No production path emits `SupplierOrderInfo` any more; the builder keeps the 1.2.071 emission for the samples alone.

**The basket.** `Cart\NativeSessionHandler` bypasses core's keying: it resolves the visit itself, hydrates and saves only its own `pow_`-keyed row, writes no WooCommerce session cookie, and refuses a non-empty visit with a 409. Inside a visit it installs `wc_session_expiration` at `PHP_INT_MAX`, returning what the visit row has left (minimum 60s) — which deliberately also caps a cart token, and is global for that request. `Docs\SelfTest::cart_handler_faults()` pins the 21 core session methods the bypass depends on; a new dependency belongs in `SelfTest::CART_HANDLER_SHAPE` in the same commit.

**Locks.** The cart mutex is per visit: `NativeSessionGuard::with_visit_lock()`, a named MySQL lock `pow_cart_<52 hex>` over the database name, table prefix and visit id, so no key or identifier appears in clear. The connection lock (`Registry::with_partner_lock`) still covers redeem, teardown, registry writes and consent. The order is always connection-then-visit; nothing inside the visit lock asks for the connection lock, and a new lock must not reverse that.

**Cart-Token.** Refused inbound, permanently: a token whose payload is a visit key, or whose numeric user id owns a connection, is denied, as is a `?session=` clone attempt inside a visit. Outbound, any `Cart-Token` header is stripped from a REST response inside a visit. An unanswerable visit lookup strips and denies.

**Ownership.** The identity fingerprint the cart guard re-proves reads only the authorising user-meta rows (`NativeSessionGuard::AUTH_META`: capabilities and user level). Adding meta a request can write mid-request would re-open the lost-cart bug. Nothing in `includes/Cart/` or `includes/Addresses/` compares a user id for ownership; `Addresses\Resolver::is_request_visit()` is the one ownership primitive in `Addresses/`, and `Cart\Guard::hides_merge_flag`'s user-id read is a meta-row scope test, documented as such.

**Delivery.** The consent record no longer names a person: `buyer_user_id` is the connection's bound login on every visit and `session_id` is the only discriminator. The policy fingerprint lost the exit policy and gained the live handler's visit key, so every stored consent from before this release fails validation and needs one fresh review — safe only because the v7 upgrade closes every open visit. The address book is admin-only and read-only inside a visit; selection still works. The last address candidate is the bound account's own profile address, i.e. the company default on a fresh visit, and it is labelled as such.

**Orders.** A quote order carries `_pow_session_id`, `_pow_partner_id`, `_pow_buyer_identity`, `_pow_buyer_name`, `_pow_buyer_cookie` and `_pow_partner_name`, plus an order note and a "Bought by" line on the admin order screen. It does not carry the visit key, and the cross-visit order fence keys on `_pow_session_id` with "absent meta is a refusal". Anything that starts stamping the key must add it to both the prepared snapshot and the attachment snapshot, or the two meta sets stop matching.

**Lockdown.** `RouteGuard` blocks wp-admin on `admin_init`, refuses `/wp/v2/users*` and `/wp/v2/application-passwords*` on `rest_pre_dispatch` with `pow_visit_locked` (403), denies application passwords outright, and blocks checkout and every My Account page the connection has not ticked, the account-details and password-change endpoints included. The locked REST prefixes live in one place, `RouteGuard::locked_route()`. HTTPS enforcement is decided by the request's own visit, not by a role or user meta.

**What the removals left behind.** `partners.mode` and `partners.exit_policy` columns remain in the schema but are never written and always read as the literals `requisition_only` and `punchout_only`; the only authorisation left on the retired exit-policy column is `Admin\Page::CAP`. Its one reader is `Partner::allows_native_checkout()` (0.4.6), which keeps the payment-method pages out of a visit's My Account list and is false for every connection. `Session::ORDERED` is inert vocabulary that nothing writes. `Cron::expire_sessions()` is the only collector of abandoned visits, and the open-visit cap depends on it; an expired visit deletes its own `wp_woocommerce_sessions` row. The plugin writes no user meta on the bound account on any request path — that absence is what makes the shared-login cart fingerprint viable. Two consequences are breaking and deliberate: there is no password-door hardening any more, so a stolen password for the bound account is an ordinary store login for that account outside any visit; and because WordPress mixes part of the password hash into the auth-cookie key, changing or resetting that password ends every live visit mid-basket, with no error and no audit row.

**My Account in a visit (0.4.5, 0.4.6).** Until 0.4.4 a visit was sent away from every My Account page, which also closed third-party account pages buyers use, such as a quick-order form. The fix is a column, not a hook:

- `partners.visit_endpoints` (schema 8, `VARCHAR(255)`, default `''`) is a comma-separated list of WooCommerce My Account endpoint names; since 0.4.6 the entry `dashboard` stands for the account page itself (`/my-account/`, no endpoint), the name WooCommerce's account menu gives it. Empty keeps all of My Account closed, exactly as in 0.4.4. A new connection gets `dashboard` from `Registry::insert()` when the writer names no list; the column default stays `''`, so no existing row and no other writer changes. There is no schema 9: a 0.4.5 row is valid as it stands and keeps its dashboard closed until someone ticks it. The account holder sees the list, read-only, on **My Account → Punchout integration**.
- The connection form (`Admin\Page::visit_endpoints_field()`, 0.4.6) is a checkbox list built when the screen renders from the account pages the site registers (`Admin\Page::registered_account_endpoints()`): WooCommerce's endpoint map (`WC()->query->get_query_vars()`) plus every WordPress rewrite endpoint registered for pages (`EP_PAGES`, not `EP_ALL`) under its query var, unless the map already holds it. The second source exists because wp-admin sees less than the shop: a plugin may add its pages to WooCommerce's map only on the front end or only for some accounts, but it registers their rewrite endpoints on every request, wp-admin included, or a permalink save from wp-admin would drop their addresses. The rows are grouped by `Account\VisitEndpoints::groups()`: the dashboard and WooCommerce's own endpoints (`VisitEndpoints::WOOCOMMERCE`, the set `WC_Query::init_query_vars()` defines, then any page a WooCommerce feature adds at run time, recognised by its `woocommerce_account_<endpoint>_endpoint` callback being defined under `WC_ABSPATH`), the plugin's own `punchout-integration` tab, **Added by other plugins** (every other name, alphabetically), and **Ticked, but not found on this site right now** (listed names no source shows, still ticked, because some plugins register a page only for some accounts). `view-order` has no row: it is folded into Orders (`VisitEndpoints::FOLDED`). A page registered under the name `dashboard` is not offered, because that name is the account page itself here. A row's label is WooCommerce's `get_endpoint_title()` where it gives one (never asked for `view-order`, whose title needs an order in the request), else the name. Each row carries the owner's note in plain words; no row is red. The payment-method rows on a punchout-only connection and the `VisitEndpoints::NEVER_OPEN` rows (logout, lost password, order-pay, order-received, the integration tab) are disabled, the latter marked "Stays closed in a visit". Below the list, **Add a page by name** is one more `visit_endpoints[]` entry, empty unless something is typed, for a page no source shows; it is checked like a ticked box, so a page unticked once can always be added back. No third-party endpoint is named in code: "added by another plugin" means "not WooCommerce's own". The checkboxes post `visit_endpoints[]` behind an empty hidden entry, so an all-unticked list clears the column; `Actions::authorise()` accepts that one field as a flat list of strings and every other field must stay scalar. A save is refused whole, with a notice naming each entry, when an entry is not a lowercase name, when a payment-method page is ticked on a connection whose exit policy does not allow native checkout, or when the list does not fit the column. `Registry::sanitise()` and `Partner::from_row()` normalise again. Saves run under the connection lock, behind `Admin\Page::CAP` like every other connection field, and are audited as `partner_saved` with the list saved.
- 0.4.5 kept a fixed hard-deny list (the dashboard, orders, order view, downloads, addresses, account details, payment methods, lost password, logout, the integration tab, order-pay and order-received). 0.4.6 removed it on the owner's decision of 23 September 2026: which pages a visit opens is the connection's choice, with the risks written beside each row. Three rules stay in code. The payment-method pages open only when `Partner::allows_native_checkout()` is true, and it is false for every connection because `exit_policy` always reads `punchout_only`; `VisitEndpoints::listed()` leaves them out of the list a visit reads, and the form shows them disabled. `VisitEndpoints::NEVER_OPEN` (logout, lost password, order-pay, order-received and the integration tab) is left out of that list too, whatever the row holds: WooCommerce has no account content for the first four, order-pay and order-received are checkout pages that checkout refusal already covers, and the tab shows nothing inside a visit (`IntegrationTab::actor()` is 0 there), so ticking them could only mislead. And the content rule below.
- `RouteGuard::guard()` opens an account page inside a visit only when every endpoint the request names is listed and has account content (a `woocommerce_account_<endpoint>_endpoint` action). An account request naming no endpoint is the dashboard and opens only when `dashboard` is listed. The content check keeps a ticked name from showing another page: `woocommerce_account_content()` renders the first query var with such an action and falls back to the dashboard when none has, so a listed name without content (a mistyped slug, a checkout endpoint, a third-party endpoint whose plugin registers its content only for some accounts) would otherwise show the dashboard. It stays closed even when the dashboard is ticked. Because every query var with an action is among the endpoints checked, the page WooCommerce renders is always a listed one, or the ticked dashboard for a request that names no endpoint. `RouteGuard::recheck_account_page()` repeats the check at the end of `template_redirect` (`PHP_INT_MAX`), so content a plugin registers after the first pass is judged too; content registered while the page itself renders is beyond any redirect. "Every endpoint" means WooCommerce's current endpoint, every endpoint of WooCommerce's own map that the request sets, and every query var an account-endpoint action would render, because WooCommerce picks the current endpoint and the rendered one in two different orders. An `?orders=` added to an allowed URL therefore closes the page. Before WordPress has parsed the request, the path and query string matched against WooCommerce's endpoint slugs stand in; a path naming none of them proves nothing, so even a ticked dashboard waits for the parsed request, and without WooCommerce's endpoint map nothing opens. A connection that is missing, not active or unreadable opens nothing. A requested endpoint named `dashboard` (a page another plugin registers under that name) never opens, since `dashboard` stands for the account page itself. Inside a visit `woocommerce_account_menu_items` (at `PHP_INT_MAX`) keeps the `dashboard` item when the dashboard is ticked and otherwise only listed items that have account content.
- **Dashboard logout link (0.4.7).** WooCommerce's dashboard template (`myaccount/dashboard.php`) opens with "Hello Name (not Name? Log out)", and `wc_logout_url()` is a wp-login.php logout that `RouteGuard::guard_login_screen()` lets through and that ends the visit and deletes its basket. `Account\VisitDashboard` filters `wc_get_template` (at `PHP_INT_MAX`) and, inside a visit or when the visit cannot be proved, renders the plugin's `templates/account/dashboard.php` instead: WooCommerce's dashboard (template version 4.4.0) without that sentence, with `woocommerce_account_dashboard` and the two deprecated dashboard hooks. It replaces a theme's copy as well; a theme overrides the visit's dashboard at `punchout-woocommerce/account/dashboard.php` or with `pow_template_account/dashboard`. `woocommerce_locate_template` is not used because WooCommerce caches its answer across requests. Logout itself, the wp-login.php door and the menu filter are unchanged; `customer-logout` was already never in a visit's menu (`VisitEndpoints::NEVER_OPEN`).
- **Temporary password.** WooCommerce shows "Your account is using a temporary password" with a Resend link on the account dashboard and on account details when the account carries the `default_password_nag` user option (set by `wc_create_new_customer()` for a generated password, and by WordPress for a self-registered account). The link's handler (`WC_Form_Handler::resend_set_password()`, `template_redirect` priority 10, any page) mails the account a new password-reset link, replaces its reset key and writes `_wc_set_password_resend_at`. Once the dashboard can be ticked, a buyer in a visit would see that link for the shared login. `RouteGuard::hide_temporary_password()` filters `get_user_option_default_password_nag` (at `PHP_INT_MAX`) to false inside a visit, or when the visit cannot be proved, so neither the notice nor its nonce renders; `RouteGuard::guard()` also refuses a request carrying `wc-resend-set-password` inside a visit, before WooCommerce's handler runs. Outside a visit, the account holder's own login included, the option is untouched.
- The list opens pages and nothing else. `admin-ajax.php` stays exempt as before and the locked REST prefixes are unchanged.
- **No user creation.** `RouteGuard::refuse_user_creation()` runs on `wp_pre_insert_user_data` at `PHP_INT_MAX` and hands core an empty user row when a user would be created inside a visit, so core returns `WP_Error( 'empty_data' )` before anything is written. Registration forms, the users REST route and plugins' AJAX actions behind the exempt `admin-ajax.php` (a sub-account form, say) all create users through that one core routine, so the plugin keeps no list of such actions. Code that writes the users table itself, without core, is outside any WordPress hook and is not covered. The refusal is audited as `visit_user_create_refused`, once per request, with the connection, the visit, the script, the `admin-ajax` action, the `wc-ajax` action, the REST route and the request path, never the refused account's details or the query string. Updates of an existing user pass untouched.
- A listed third-party page runs as the shared account. Anything it stores per user (a saved list, a draft) is stored once for the whole connection: every buyer sees and can change it, and nothing records which buyer did. Decide that per connection before listing such a page. Theme and page-builder links to account pages are not menu items; gate them on `POW\pow_is_punchout()`.

**Guards in the suite.** `ProvisioningRemovalTest`, `DualExitRemovalTest` and `NativeSuiteShapeTest` scan shipped source and the opt-in scripts for the removed vocabulary; a ticket that reintroduces one of those strings, including in a comment, fails them. `tests/Support/visit-key-database.php` and `tests/Support/native-visits.php` are the shared multi-visit fixtures. Test counts are per suite, not one run: `php tests/run-tests.php`, `php tests/CartBlocks/surface.php`, `node --test tests/CartBlocks/cart-blocks.test.js`, `php tests/Admin/run.php` and `php tests/Account/run.php` each report their own.
