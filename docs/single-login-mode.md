# Single-login mode — v0.4.0 (breaking)

Confirmed by the owner on 21 September 2026 after grilling. Replaces every earlier variant (per-employee accounts, separate bound-login field, dual exit, front-end self-service). Nothing in an earlier copy of this file, in a ticket packet or in a review note survives where it disagrees with what is written here.

The model and decisions below are the specification. **How the build landed** records what the merged code actually does, and is the section to read before touching the areas it names.

## The rule

The plugin does its whole job on any WordPress site with WooCommerce and nothing else. No site file, no mu-plugin, no hook whose purpose is site glue, no knowledge of any other plugin. Buyers are signed in as the customer's own account and see exactly what that account sees.

## The model

1. **The connection's customer account is the login.** `partners.owner_user_id` (already there) is the account buyers punch in as. No separate binding field, no password flag. It is bound on the connection's own edit screen and cannot be transferred or cleared afterwards. A usable account exists, can `read`, and holds none of `Registry::PRIVILEGED_CAPABILITIES`; the same test refuses the binding, refuses setup and refuses the redeem. A connection with no usable account refuses `PunchOutSetupRequest` with cXML 500, an audit row (`setup_no_login`) and a persistent admin notice.
2. **The plugin never creates, renames or deletes users.** `Buyers\Provisioner`, ephemeral identities, the `punchout_buyer` role, the identity mutex, latest-wins, the dormant-buyer cron and the hooks `pow_buyer_provisioned` / `pow_buyer_deactivated` are removed. No migration tooling.
3. **One WooCommerce session row per visit.** Every setup request gets its own WP auth cookie and `WP_Session_Tokens` entry for the customer account and its own `wp_woocommerce_sessions` row keyed by a per-visit key (`pow_` + 28 hex = 32 chars, UNIQUE in `sessions.wc_session_key`, minted inside `Store::bind_login()`). Two employees at once = one WP user, two visits, two baskets, two delivery selections. The same buyer identity punching in again supersedes only its own earlier visit. Open visits per connection are capped. A visit is a row, not a person: many open rows for one `user_id` is the normal state.
4. **Buyer identity is data.** Name and e-mail from the cXML request (UserEmail → UniqueUsername → UniqueName → Contact/Email; UserPrintableName → UserFullName → User) live on the session row (`buyer_identity`, `buyer_name`, `buyer_identity_hash`; empty allowed) and are stamped on the quote order as meta (`_pow_buyer_identity`, `_pow_buyer_name`, `_pow_buyer_cookie`), an order note and a "Bought by" line on the admin order screen. `customer_id` stays the customer account. No e-mails to buyers.
5. **PunchOut only.** The "PunchOut and checkout" exit, `Checkout\PayExit` and the per-buyer exit policy are removed. Checkout is blocked inside a visit.
6. **Admin-only management.** The front-end application flow and every My Account action are removed. The My Account "Punchout integration" tab keeps only the read-only setup XML download (placeholder secret) for the account holder while the connection is active, and is unreachable during a visit.
7. **Shared-login lockdown.** Inside a visit the request cannot reach wp-admin, `/wp/v2/users*`, application passwords, account details or password change, another visit's basket, or another visit's quote order. Every "is this mine" check compares the per-visit key, never the user id. Every door fails closed: a visit lookup that cannot run answers "in a visit".

## Decisions on the open points (owner delegated these; do not reopen)

1. Audit log: no new column. Setup rows put `buyer_hash` (sha256 of partner_id|identity, first 12 hex) and `buyer_name` in the detail JSON; never the raw email in the log.
2. Delivery consent JSON gains `buyer_identity` and `buyer_name` beside `buyer_user_id` (which is now the shared account and no longer discriminates). `session_id` remains the key.
3. Open-visit cap per connection: constant `Store::MAX_OPEN_VISITS = 50`, no filter. Expired rows are swept before counting.
4. Raw buyer identity (usually an email) is stored in cleartext on the session row (`buyer_identity`) and on the quote order (`_pow_buyer_identity`) because admins must see who bought; the indexed column is `buyer_identity_hash`.
5. Anonymous visit: no new audit event; `setup_ok` detail carries `buyer: none`.
6. Owner e-mails that belonged to the front-end registration flow go with it. Admin-created connections send nothing. The pending/approve/reset admin lifecycle stays as is (harmless, no producer).
7. `partners.mode` and `partners.exit_policy` columns stay; only `requisition_only` / `punchout_only` are ever written or honoured. Checkout is blocked inside every visit.
8. `[punchout_cart_exits]` keeps rendering the native checkout link for ordinary shoppers outside a visit; inside a visit only the return control renders.
9. `Session::ORDERED` stays as inert vocabulary; nothing writes it after PayExit goes.
10. A fresh visit's customer snapshot is seeded from the bound account's profile address, labelled "Company address" (not "Your current delivery address"); the delivery review still decides.
11. "Bought by" wording. Admin line and order note: `Bought by {name} <{email}> via PunchOut ({connection name})`; when name is empty use the email alone; when nothing was supplied: `Bought by an unnamed buyer via PunchOut ({connection name}); the purchasing system sent no name or e-mail`.
12. Tautology guard: a unit test greps `includes/` and fails when `get_customer_id()` appears within three lines of `user_id` or `get_current_user_id()` outside `includes/Cart/SessionKey.php`.
13. `docs/single-login-mode.md` keeps its name.
14. B2BKing, or any other plugin, is never named in code or in-plugin strings; docs may say "your pricing or visibility plugin".

## How the build landed

One paragraph per area, naming the load-bearing decision a later change has to respect.

**The visit key.** `POW\Cart\SessionKey` mints it: `pow_` plus 28 hex, `SessionKey::LENGTH` 32 characters, self-checked at mint. `is_visit_key()` accepts lowercase hex only and is the shape test; `for_session()` resolves a visit's own basket. `Store::bind_login( id, token, expires, key )` writes the login token and the key in one guarded UPDATE that requires an active row, an unbound token and a NULL key, then reads all four back; `StartEndpoint` retries once with a fresh key, which can only win a UNIQUE collision. Nothing else writes the column — `Store::create()` deliberately leaves it NULL at setup, which is why the column must stay nullable with no default.

**Resolving a visit.** There are two resolvers and they are not interchangeable. `Store::find_for_login( user_id, wp_session_token )` is the login side; its `ORDER BY id DESC LIMIT 1` and its non-BINARY token comparison are both load-bearing (the comparison keeps the `(user_id, wp_session_token)` index in play). `Store::find_by_wc_session_key()` is the basket side. `Sessions\Current::visit()` is the one request-scoped resolver over the login side, and `Plugin::current_session()` memoises only a conclusive answer. A resolver that throws does not mean "no visit" — every caller either propagates or fails closed.

**Setup.** `Buyers\Identity::from_message()` reads the identity and the name; `Identity::hash( partner_id )` is `sha256( partner_id . '|' . identity )` and the full 64 hex goes in `buyer_identity_hash`, while the audit detail carries only the first 12. Supersede is `Store::open_for_identity( partner_id, identity_hash )`, so an anonymous visit supersedes nothing. The cap is enforced once, in `SetupEndpoint::refuse_over_cap()`, inside the connection lock and before the insert; it sweeps this connection's expired-but-open rows first, because another connection's rows belong to another lock. A replay of an existing `(partner_id, payload_id)` returns before the cap is consulted, on purpose: a lost response must stay re-deliverable at the cap.

**Redeem and return.** The StartPage sets the auth cookie directly and never fires `wp_login`, so WooCommerce never writes the saved-cart-after-login flag for a visit. Setup re-proves the bound account inside the connection lock before it commits the visit, and answers 500 if the binding changed under it. The redeem proves it once more: the claim's user must be the connection's own owner, and that account must exist, be able to `read`, hold no privileged capability and carry no legacy `_pow_partner_id` user meta. The return winner guard compares the re-read row's key with the snapshot's, byte-exactly, in addition to the guarded-transition predicates. No production path emits `SupplierOrderInfo` any more; the builder keeps the 1.2.071 emission for the samples alone.

**The basket.** `Cart\NativeSessionHandler` bypasses core's keying: it resolves the visit itself, hydrates and saves only its own `pow_`-keyed row, writes no WooCommerce session cookie, and refuses a non-empty visit with a 409. Inside a visit it installs `wc_session_expiration` at `PHP_INT_MAX`, returning what the visit row has left (minimum 60s) — which deliberately also caps a cart token, and is global for that request. `Docs\SelfTest::cart_handler_faults()` pins the 21 core session methods the bypass depends on; a new dependency belongs in `SelfTest::CART_HANDLER_SHAPE` in the same commit.

**Locks.** The cart mutex is per visit: `NativeSessionGuard::with_visit_lock()`, a named MySQL lock `pow_cart_<52 hex>` over the database name, table prefix and visit id, so no key or identifier appears in clear. The connection lock (`Registry::with_partner_lock`) still covers redeem, teardown, registry writes and consent. The order is always connection-then-visit; nothing inside the visit lock asks for the connection lock, and a new lock must not reverse that.

**Cart-Token.** Refused inbound, permanently: a token whose payload is a visit key, or whose numeric user id owns a connection, is denied, as is a `?session=` clone attempt inside a visit. Outbound, any `Cart-Token` header is stripped from a REST response inside a visit. An unanswerable visit lookup strips and denies.

**Ownership.** The identity fingerprint the cart guard re-proves reads only the authorising user-meta rows (`NativeSessionGuard::AUTH_META`: capabilities and user level). Adding meta a request can write mid-request would re-open the lost-cart bug. Nothing in `includes/Cart/` or `includes/Addresses/` compares a user id for ownership; `Addresses\Resolver::is_request_visit()` is the one ownership primitive in `Addresses/`, and `Cart\Guard::hides_merge_flag`'s user-id read is a meta-row scope test, documented as such.

**Delivery.** The consent record no longer names a person: `buyer_user_id` is the connection's bound login on every visit and `session_id` is the only discriminator. The policy fingerprint lost the exit policy and gained the live handler's visit key, so every stored consent from before this release fails validation and needs one fresh review — safe only because the v7 upgrade closes every open visit. The address book is admin-only and read-only inside a visit; selection still works. The last address candidate is the bound account's own profile address, i.e. the company default on a fresh visit, and it is labelled as such.

**Orders.** A quote order carries `_pow_session_id`, `_pow_partner_id`, `_pow_buyer_identity`, `_pow_buyer_name`, `_pow_buyer_cookie` and `_pow_partner_name`, plus an order note and a "Bought by" line on the admin order screen. It does not carry the visit key, and the cross-visit order fence keys on `_pow_session_id` with "absent meta is a refusal". Anything that starts stamping the key must add it to both the prepared snapshot and the attachment snapshot, or the two meta sets stop matching.

**Lockdown.** `RouteGuard` blocks wp-admin on `admin_init`, refuses `/wp/v2/users*` and `/wp/v2/application-passwords*` on `rest_pre_dispatch` with `pow_visit_locked` (403), denies application passwords outright, and blocks checkout and the account-details and password-change endpoints. The locked REST prefixes live in one place, `RouteGuard::locked_route()`. HTTPS enforcement is decided by the request's own visit, not by a role or user meta.

**What the removals left behind.** `partners.mode` and `partners.exit_policy` columns remain in the schema but are never written and always read as the literals `requisition_only` and `punchout_only`; the only authorisation left on the retired exit-policy column is `Admin\Page::CAP`. `Session::ORDERED` is inert vocabulary that nothing writes. `Cron::expire_sessions()` is the only collector of abandoned visits, and the open-visit cap depends on it; an expired visit deletes its own `wp_woocommerce_sessions` row. The plugin writes no user meta on the bound account on any request path — that absence is what makes the shared-login cart fingerprint viable. Two consequences are breaking and deliberate: there is no password-door hardening any more, so a stolen password for the bound account is an ordinary store login for that account outside any visit; and because WordPress mixes part of the password hash into the auth-cookie key, changing or resetting that password ends every live visit mid-basket, with no error and no audit row.

**Guards in the suite.** `ProvisioningRemovalTest`, `DualExitRemovalTest` and `NativeSuiteShapeTest` scan shipped source and the opt-in scripts for the removed vocabulary; a ticket that reintroduces one of those strings, including in a comment, fails them. `tests/Support/visit-key-database.php` and `tests/Support/native-visits.php` are the shared multi-visit fixtures. Test counts are per suite, not one run: `php tests/run-tests.php`, `php tests/CartBlocks/surface.php`, `node --test tests/CartBlocks/cart-blocks.test.js`, `php tests/Admin/run.php` and `php tests/Account/run.php` each report their own.
