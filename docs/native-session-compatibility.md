# Punchout native cart session compatibility

Punchout uses WooCommerce's own session table and the customer account's normal WordPress authentication. What it does not use is the WooCommerce session cookie: a punchout row is keyed by the visit, not by the shopper. Each visit is signed in on the connection's bound customer account with its own WordPress auth cookie and its own `WP_Session_Tokens` entry, and carries its own 32-character `pow_`-prefixed key, UNIQUE in the plugin's session table. The extension of the default `WC_Session_Handler` resolves that visit before cart hydration, reads the visit's own row, and saves only when that row still matches the value this request loaded or last successfully saved. This prevents an older request from overwriting a newer cart or approving its old contents. Ordinary shoppers — the bound account's own browsing included — run the default handler byte for byte.

Two visits of one account are two rows, and no request may read, write or delete another visit's row. Every ownership question in this area is answered by comparing the per-visit key, never the signed-in user id: under one shared login a user-id test would give every concurrent visit authority over every other visit's basket. A key that is not this request's own is refused outright rather than passed to the inherited storage path, and a foreign or absent key reads as the default and is never written.

Supported Punchout paths are the default cookie session handler, storefront/classic cart requests, and Store API requests authenticated with the buyer's cookies and WooCommerce Nonce. Comparison covers the whole native row. When only the native row changed under a request, the request reloads the row once and replays only the keys it changed itself on top of the concurrent value; a second conflict, or any identity or consent refusal, is final. A final refusal can require reloading the cart and reviewing delivery again; it is logged at warning level (hashed session key and reason, no session data) in the `punchout-woocommerce` operational log. Once refused, the request cannot retry its old data at shutdown.

Cart-Token requests targeting a punchout visit's session row are refused. This is permanent, not provisional. The check uses WooCommerce's authenticated token payload from the outer HTTP request, including when there is no logged-in WordPress actor, and it refuses both a token whose payload is a visit key and one whose numeric payload names an account a connection is bound to. Core's `?session=` clone path — which validates the parameter, generates a customer id, re-cookies it and copies that basket's data onto this row — is refused inside a visit for the same reason. The refusal also runs outbound: any `Cart-Token` header is stripped from a REST response served inside a visit, so a visit key can never leave as a bearer credential. Ordinary customers' Cart-Token requests retain WooCommerce behavior. The native Store API token handler is a separate final class; it is not silently replaced with cookie authentication. Supporting it for punchout would require a guarded native adapter and separate acceptance tests.

Other plugins' custom session handlers are not silently replaced. A punchout request using an unsupported handler is refused, and a visit lookup that cannot be answered refuses too rather than passing for an ordinary shopper. Installations using custom native session persistence need an explicitly reviewed integration before enabling that path. Direct writes to WooCommerce's session table outside its selected handler cannot participate in this guard and are unsupported for punchout.

Protected sessions must contain native scalar/array session data. Opaque objects or recursive data are refused. No guest session is ever migrated into a punchout visit: core's guest-to-user migration and its clone path both live inside the private initialisation this handler bypasses, so neither is reachable during a visit. The existing create/edit cart-seeding policy remains the only thing that fills a punchout basket.

Because the handler bypasses core's initialisation, it depends on core internals staying as they are. The shape of the inherited handler is therefore proved on every punchout request before the bypass runs, and a changed or re-scoped core session method refuses the visit with a 409 instead of silently mis-keying a basket. The same check is reported on the documentation self-test page.

The cart-commit lock is keyed to the visit: two visits on one account commit concurrently and never serialise against each other. The per-connection lock stays for redeem, teardown, registry writes and consent storage, and the order is always connection-then-visit; nothing inside the visit lock asks for the connection lock. Neither lock is held for the length of a request, neither adds a second return transition, and neither creates a database table. Shipping calculations, native authentication, mapping and session serialization happen before the persistence critical section. Readback failures do not count as successful saves, and protected cache entries are invalidated rather than populated with a potentially stale candidate. No cache entry is ever written under a visit key: the inherited object-cache paths are keyed on the customer id with no per-visit isolation, so a visit answers those reads and writes itself.

A visit's expiry is its own. Inside a visit the request's WooCommerce session lifetime is capped at what the visit row has left, which also stops a Store API cart token outliving the visit that issued it.

Terminal cleanup removes only the unchanged native row for its own visit key, and only while that key is this request's. A stale or superseded request cannot delete a row or recreate one during shutdown, an invalid-cookie initialisation does not authorise deleting a protected row, and a sibling visit staying open does not block cleanup of the one that ended. An expired visit also deletes its own row when it is swept, so an abandoned visit leaves nothing behind. Normal WooCommerce expiry housekeeping remains in place and is the only collector of rows this plugin does not clean itself.

Cross-request preservation of unconfirmed address-choice and notes drafts is deferred UX. It is separate from native session concurrency and persisted buyer consent.

These are plugin compatibility boundaries, not a claim that every WooCommerce extension or native request flow has been certified. Native acceptance must verify actual selected handlers and directly stored rows across independent requests, with two concurrent visits of one account, in addition to the isolated source tests.

A handler that was refused during initialization never loads a row, so its shutdown save is skipped silently: there is nothing to commit and nothing to log. This is the normal state of the StartPage redeem request, whose new login cookie is not visible to the request that set it; the next request binds the visit normally.

## Consent recovery fence

When buyer delivery consent cannot be verifiably removed after a cart change or an unacknowledged save, one module decides what happens next: `POW\Sessions\ConsentFence::clear_locked()`. It removes consent, or expires the exact visit it was given, or if that lost too, disables the connection. The visit it acts on is matched on its id, connection, account and login token together, so a replacement visit or a completed return is never expired or fenced in another visit's name. Both the delivery review (`Addresses\Confirmation`) and the cart-change hooks (`Addresses\Chooser`) call it under the connection mutex; neither carries its own copy any more. Tests: `tests/Unit/ConsentFenceTest.php`.
