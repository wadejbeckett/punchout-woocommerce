# Transport and deployment

Production and staging require HTTPS for PunchOut. Only an explicitly configured WordPress `local` or `development` environment permits HTTP. Missing or invalid environment configuration defaults to production. cXML `deploymentMode="test"` and `WP_DEBUG` do not grant an exception. The policy uses native [`wp_get_environment_type()`](https://developer.wordpress.org/reference/functions/wp_get_environment_type/) and [`is_ssl()`](https://developer.wordpress.org/reference/functions/is_ssl/).

The plugin refuses insecure Setup, Start, Return, delivery review, the account setup-XML download, supplier administration and documentation/self-test requests. The Woo AJAX return alias and delivery shortcode use the same policy. Setup and the unsupported order endpoint retain HTTP 200 with cXML status 401 for an insecure request; browser/UI requests receive 403. Refusals are private and non-cacheable, with no credential-bearing redirect. Documentation is also refused on HTTP because its page contains a self-test form that accepts credentials.

A request carrying a live punchout visit also requires HTTPS while using the ordinary catalog, cart and Store API. A native current-user check runs before Woo initializes, with a second REST check before dispatch for identities resolved during authentication. The marker is the request's own visit, not a role and not stored user meta: there is no punchout role any more, and asking anything about the user would answer "ordinary shopper" for every buyer. A second signal covers the account rather than the visit: the customer account a connection is bound to requires HTTPS whether or not a visit is open, because it is the login every buyer of that connection arrives on and its cookie must never cross the wire in cleartext. Ordinary non-PunchOut commerce by any other account remains under WordPress/WooCommerce behavior. A lookup that cannot run answers "punchout", so the refusal fails closed.

Setup requires a secure absolute BrowserFormPost target before opening a visit. Return validates the saved target again before preparing either cart or empty handoff and checks the re-read visit's target before the winner transition. An existing visit with an insecure target must be replaced by a new setup using the buyer's correct HTTPS URL. The receiver is never upgraded or changed on the buyer's behalf. New supplier protocol links and StartPage URLs use HTTPS in production/staging, while local/development URLs retain their configured scheme.

## Supplier configuration

Configure the site's canonical WordPress/WooCommerce origin and purchasing-system supplier URL as HTTPS. Use valid certificates on both supplier and buyer receiver origins. Configure TLS enforcement at the edge or web server before sensitive requests reach PHP. The plugin cannot undo exposure of a credential or token that a client already sent over HTTP, and it adds no site-wide redirects, host configuration or TLS termination.

Behind a reverse proxy, configure trusted proxy/edge TLS handling so WordPress receives accurate native HTTPS/server state. Restrict direct origin access and strip or overwrite client-supplied proxy headers at that trusted boundary. The plugin never treats arbitrary `Forwarded` or `X-Forwarded-Proto` headers as proof of TLS. Follow the official [WordPress HTTPS administration guidance](https://developer.wordpress.org/advanced-administration/security/https/), including native `FORCE_SSL_ADMIN` where appropriate; that setting alone does not guard custom frontend endpoints or external BrowserFormPost destinations.

Bypass full-page/CDN caching for authenticated shopping, `/punchout/*`, return AJAX, delivery review, the admin connection screens, and privileged or submitted self-tests. Serve POSTs directly to the canonical HTTPS endpoint without dropping their body or sending a browser challenge. Test on isolated infrastructure with explicit `WP_ENVIRONMENT_TYPE` of `local` or `development` when HTTP is necessary; never use that exception on a publicly exposed production deployment.
